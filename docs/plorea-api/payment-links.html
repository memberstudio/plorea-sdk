Payments

Payment links

A payment link is a hosted page on pay.plorea.no that takes one payment for one amount. You create the link on your server, send the customer to it, and read the result back by your own reference. Payment links are the simplest way to take a one-off payment with Plorea.

When to use a payment link

Use a payment link when the customer pays one amount once. Typical cases are an invoice, a drop-in class, a deposit or a one-time fee.

  • Hosted page. Redirect the customer to paymentLinkUrl, or open it in a WebView. You need no client key and no origin whitelisting.
  • Your own checkout. Create the link first, then open a Drop-in session on it. See Embedded and native checkout. The link is still the payment record.
  • Recurring billing. Do not use payment links. Store a card and create a subscription.

The workflow

Create a payment link

POST/payments/link

The request creates a link and returns its URL immediately. Nothing is charged yet. The link stays payable until it expires or is paid.

Request body

FieldTypeDescription
referencerequiredstringYour unique key for this payment. Use it for status, refund, cancel and webhook correlation. Use your own invoice or order number. Plorea does not reject duplicates. See Duplicate references.
productrequiredstringThe text the customer sees on the pay page, for example Invoice 2026-00123.
amountrequiredintegerThe amount in minor units (øre). 450000 is 4 500,00 kr. A flat integer here, not an object.

merchantNameoptionalstringThe issuer's legal name. Recommended. Plorea uses it in KYC communication.
merchantEmailoptionalstringWhere Plorea sends the merchant's onboarding (KYC) email. Recommended.
merchantPhoneoptionalstringThe issuer's phone number, for KYC.
merchantCountryoptionalstringThe issuer's country. The allowed format is not documented. Open question
emailoptionalstringThe payer's email. Adyen can send a payment confirmation to it.
orderIdoptionalstringYour own order id. Use it to group several payment attempts (several references) for one order. Echoed on the status body.

The response does not echo the merchant

The create response leaves out merchantOrgNr and merchantName. To confirm that Plorea stored them, read the pay page with GET /pay/{paymentLinkId}. Verified

Expiry

Plorea sets expiresAt. The request has no field to choose the lifetime, and the default lifetime is not documented. Open question Observed links expired about ten weeks after creation, but do not rely on that. Read the value from each response.

The merchant: who gets paid

Plorea is a platform. One API key can take payments for many companies. merchantOrgNr tells Plorea which company receives the payout. Always send the organisation number of the invoice issuer, for example the gym or club that sent the invoice. Never send your own platform's number unless you issued the invoice.

  • Not enforced. The API accepts a link without merchantOrgNr. It even opens a checkout session on it. The payout then has no owner. Verified The PHP SDK refuses to create such a link and throws PloreaException.
  • KYC starts by itself. The first payment for a new organisation number starts merchant onboarding. The merchant gets an email, at merchantEmail when you send one. Stated by Plorea
  • The link stays payable during KYC. Plorea holds the payout until KYC is approved. This typically takes 1–5 business days. Stated by Plorea
  • No store. Do not send store or a balance account. Plorea resolves both from the organisation number.

What we would like from Plorea

Validate merchantOrgNr on link create, the same way subscriptions already reject a value that is not 9 digits. Echo the merchant fields in the create response. Proposal

The return URL

After the attempt, the pay page sends the customer to returnUrl. The customer arrives there both after a success and after giving up.

  1. Build the URL on your server.Never copy a return URL from a request parameter. That is an open redirect.
  2. Put your own identifier in the path.For example /invoices/123/paid. Do not expect Plorea to append a reference or a result. What the pay page appends is not documented. Open question
  3. Read the status on the server.On the return page, call GET /payments/status/{reference}. Show "paid" only when the status is authorised or paid.
  4. Handle "still open".The webhook can arrive after the customer. Show "processing" and refresh, or wait for the webhook.

The redirect is not proof of payment

A customer can open the return URL without paying. The status call or a signed webhook is the only proof.

Duplicate references and firstOrCreate

The API has no idempotency. Two POST /payments/link calls with the same reference create two links. Both are payable. A customer who double-clicks, or a job that retries after a timeout, can therefore be charged twice for one invoice. Verified

Do not retry a link create blindly. Check for an existing link first. The PHP SDK does this in firstOrCreate(). You can build the same logic in any language:

State of the existing referenceAction
Unknown (404)Create the link.
Open (created, pending, active), same amount, currency, tenant and environment, and the pay page says expired: falseReuse it.
Open but expired, or a different amount, or dead (cancelled, refunded, failed)Create a new link on a suffixed reference: INV-2026-00123-1, then -2, and so on.
Paid (authorised, paid)Stop. Never create a new link for a paid invoice.

Two details make this correct:

  • Walk the whole suffix chain. A superseded reference stays created forever. Nothing changes it when the customer pays the -1 link. So check every suffix, and one past the last, before you reuse a link. Otherwise you can hand out an old link while a newer one is already paid.
  • Judge expiry from the pay page. The status endpoint has no expiry field, and its status never becomes expired.
use Illuminate\Support\Facades\Cache;
use MemberFlow\Plorea\Exceptions\PaymentAlreadyPaidException;

try {
    // Serialise per reference: firstOrCreate() is not atomic.
    $link = Cache::lock("plorea:{$invoice->reference}", 10)->block(5, fn () => Plorea::payments()
        ->link($invoice->reference, $invoice->title, Amount::nok($invoice->ore), route('invoices.paid', $invoice))
        ->merchant(orgNr: '999999999', name: 'Acme Gym AS')
        ->firstOrCreate());
} catch (PaymentAlreadyPaidException $e) {
    // $e->status->reference may be a suffixed reference, e.g. INV-2026-00123-1.
    $invoice->markPaid($e->status);
}
// plorea(method, path, body?) wraps fetch with the auth and
// X-Environment headers and returns the Response.
const OPEN = ['created', 'pending', 'active'];
const PAID = ['authorised', 'paid'];

async function firstOrCreate(base, payload, maxAttempts = 10) {
  let reusable = null;
  for (let i = 0; i <= maxAttempts; i++) {
    const reference = i === 0 ? base : `${base}-${i}`;
    const res = await plorea('GET', `/payments/status/${encodeURIComponent(reference)}`);
    if (res.status === 404) {
      // End of the chain: reuse the last open link, or create here.
      return reusable ?? plorea('POST', '/payments/link', { ...payload, reference });
    }
    const status = await res.json();
    if (PAID.includes(status.status)) throw new Error(`Already paid as ${reference}`);
    const page = OPEN.includes(status.status) && status.paymentLinkId
      ? await plorea('GET', `/pay/${status.paymentLinkId}`).then((r) => r.json())
      : null;
    const sameTerms = status.amount === payload.amount && status.currency === payload.currency;
    reusable = page && !page.expired && sameTerms ? status : null;
  }
  throw new Error('Too many superseded links');
}

Two caveats

  • The check-then-create is not atomic. Two requests that race on a new reference can both create a link. Hold a lock per reference.
  • The suffix scheme assumes that {reference}-1 is never a real invoice number in your system.

What we would like from Plorea

Reject a duplicate reference with 409 and return the existing link, or accept an Idempotency-Key header. Then the suffix walk is no longer necessary. Proposal

Reconcile the result

Three signals can tell you about the outcome: the webhook, the customer's return, and your own status poll. They can arrive in any order, and the webhook can be lost. Plorea does not redeliver a failed webhook. Stated by Plorea

  1. Treat every signal as a ping.On any of the three, call GET /payments/status/{reference}.
  2. Compare the amount.Check amount and currency against your invoice. Flag a mismatch for manual handling. Do not book it automatically.
  3. Book idempotently.Key the booking on the reference. A second signal must not book the payment twice.
  4. Poll open links as a backstop.Run a scheduled job over links that are open and not expired. Stop polling when expiresAt has passed.
  5. Store the identifiers.Keep reference, paymentLinkId, pspReference and expiresAt. Support at Plorea and Adyen asks for the PSP reference.
$status = Plorea::payments()->status($invoice->plorea_reference);

if ($status->isPaid()) {
    if ($status->amount?->value !== $invoice->ore) {
        $invoice->flagForReview('Plorea amount mismatch');
        return;
    }
    $invoice->markPaid($status);   // idempotent on the reference
} elseif ($status->is('failed')) {
    $invoice->markDeclined();      // the customer can try again on a new link
}
const s = await plorea('GET', `/payments/status/${ref}?platform=acme`).then((r) => r.json());

if (['authorised', 'paid'].includes(s.status)) {
  if (s.amount !== invoice.ore) return flagForReview(invoice);
  await markPaid(invoice, s.pspReference); // idempotent on the reference
} else if (s.status === 'failed') {
  await markDeclined(invoice);
}

A declined payment reports failed, never refused. The status body has no decline reason. Verified See Payment lifecycle and states for all statuses.
