Reference

Gaps and proposals

What integrators need from Plorea next. Each item states the problem, what it costs an integrator today, and a proposed API shape. The shapes are suggestions to start a conversation. Plorea knows its system best and should change them freely.

Why this page exists

The Plorea API already covers the core flows well. Plorea has been quick to answer questions and to fix issues, often within a day. The items below are the gaps we met while building a production integration. Most of them cost integrators extra code, extra polling or support cases. Closing them makes Plorea easier to adopt.

Payments

1. Idempotency keys

Problem. Two identical POST /payments/link calls create two payable links. The same is true for POST /subscriptions and POST /subscriptions/{id}/charge. A network timeout leaves the integrator unsure whether the call succeeded. Verified

Impact. Integrators cannot retry safely. A retry after a timeout can bill a customer twice. Today each integrator must look up the payment first and invent a suffix scheme for new references.

Proposal. Accept an Idempotency-Key header on every POST. Store the first response for 24 hours. Return it again for the same key and the same body. Return 409 for the same key with a different body.

POST /payments/link
Idempotency-Key: acme-order-1001-attempt-1
X-Environment: test
HTTP/1.1 200 OK
Idempotent-Replayed: true

5. Refusal reason

Promised by Plorea Plorea has stated that refusalReason is coming on GET /payments/status/{reference}.

Problem. A declined payment shows only status: "failed" and webhookSuccess: false. No reason exists on the payment, the webhook, the payment method or the charge.

Impact. Integrators cannot tell the customer what to do. "Insufficient funds" needs a different message than "card expired" or "3-D Secure failed". Support cannot answer "why was I declined?".

Proposal. Add Adyen's refusal data to the payment, the payment.failed webhook, the payment method and each charge. Keep the raw code and add a stable category.

{
  "status": "failed",
  "refusalReason": "Not enough balance",
  "refusalReasonCode": "51",
  "refusalCategory": "insufficient_funds"
}

7. Capture API and captured state

On Plorea's roadmap Plorea has stated that a manual capture API is planned.

Problem. Capture is automatic. No status, field or webhook shows that capture happened. authorised is the last success state an integrator can see.

Impact. Integrators cannot tell whether to cancel or to refund. A cancel after capture fails, and a refund before capture is wrong. Businesses that ship goods later cannot hold an authorisation and capture on shipment.

Proposal. Add a captured status and a payment.captured event. Add an optional manual mode with a capture endpoint.

{ "reference": "order-1001", "amount": 10000, "currency": "NOK", "captureMode": "manual" }
{ "reference": "order-1001", "amount": 10000, "modificationReference": "order-1001-CAPTURE-1" }
{ "status": "captured", "capturedAt": "2026-10-01T12:03:00Z", "capturedAmount": 10000 }

8. Per-refund status

Problem. The payment shows only the last refund. refundPspReference exists only on the refund response. The payment carries only last-refund fields. Verified So a second partial refund would hide the first one. We infer this from the shape; we did not run two partial refunds.

Impact. Integrators cannot reconcile several partial refunds. A lost refund response loses the refund's own reference forever.

Proposal. Return a list of refunds on the payment, each with its own status.

{
  "reference": "order-1001",
  "status": "authorised",
  "refundedAmount": 3000,
  "refunds": [
    {
      "modificationReference": "order-1001-REFUND-1",
      "pspReference": "TESTREFUNDPSP001",
      "amount": 3000,
      "status": "refunded",
      "requestedAt": "2026-10-01T12:00:00Z",
      "settledAt": "2026-10-01T23:10:00Z"
    }
  ]
}

9. Expired status

Problem. A payment link past expiresAt keeps its open status. An abandoned session stays created forever. Verified

Impact. Integrators must store expiresAt and compute expiry themselves. Reports show stale open payments.

Proposal. Report expired on the status endpoint once expiresAt passes. Optionally send payment.expired.

{ "reference": "order-1001", "status": "expired", "expiresAt": "2026-10-08T12:00:00Z" }

Subscriptions

2. Failed charge webhook and payment_failed

Problem. A failed scheduled charge sends no webhook. Stated by Plorea The payment_failed status, failureReason and retryCount have never been observed.

Impact. This is the most important event in recurring billing. Integrators must poll every subscription to find failures. Customers keep access they did not pay for, or lose access without a warning.

Proposal. Send subscription.charge_failed on each failed attempt, and subscription.payment_failed when retries run out.

{
  "eventId": "evt_00000000000000000000000000000003",
  "type": "subscription.charge_failed",
  "tenantId": "acme",
  "data": {
    "subscriptionId": "sub_test_example",
    "chargeId": "chg_test_example_3",
    "reference": "sub_test_example-chg_test_example_3",
    "externalId": "membership-001",
    "amount": { "value": 29900, "currency": "NOK" },
    "retryNumber": 1,
    "maxRetries": 3,
    "nextRetryAt": "2026-10-02T10:00:00Z",
    "refusalReason": "Not enough balance",
    "refusalCategory": "insufficient_funds",
    "environment": "test"
  }
}

10. Pause and resume

Problem. No pause exists. To freeze a membership, integrators cancel and create a new subscription with a trial until the resume date, or cancel and later reactivate. Reactivate sets nextChargeAt to one interval after the last charge, which can lie in the past.

Impact. Freezes are common in memberships, for example during illness or travel. The workaround changes the subscription ID, splits the charge history and needs careful date maths.

Proposal.

{ "resumesAt": "2026-12-01T00:00:00Z", "reason": "medical" }
{ "subscriptionId": "sub_test_example", "status": "paused", "pausedAt": "2026-10-10T09:00:00Z", "resumesAt": "2026-12-01T00:00:00Z", "nextChargeAt": "2026-12-01T00:00:00Z" }

Add POST /subscriptions/{id}/resume to end a pause early, and events subscription.paused and subscription.resumed.

11. Interval change

Problem. PATCH /subscriptions/{id} cannot change interval.

Impact. A move from monthly to yearly needs a cancel and a new subscription, timed to accessEndsAt.

Proposal. Accept interval on PATCH, effective from the next charge.

{ "interval": { "unit": "year", "count": 1 }, "amount": { "value": 299000, "currency": "NOK" }, "effective": "next_charge" }

12. Proration

Problem. A mid-cycle upgrade has no proration. Integrators compute the difference and send a manual charge. A downgrade needs a refund of a scheduled charge, and it is unclear whether that works.

Impact. Every integrator writes the same date and VAT maths.

Proposal. An optional proration flag on PATCH, and a preview endpoint.

{ "amount": { "value": 49900, "currency": "NOK" }, "proration": "charge_now" }
{ "prorationCharge": { "chargeId": "chg_test_example_4", "amount": { "value": 13300, "currency": "NOK" } } }

14. Scheduled charges on the status endpoint

Reported to Plorea

Problem. The reference of a scheduled charge returns 403 or 404 on GET /payments/status. A manual charge reference works.

Impact. Integrators need two code paths to read a charge. A refund of a scheduled charge may not be possible.

Proposal. Resolve every charge reference on the status endpoint, with platform: "subscription", as manual charges already do.

15. Pagination

Problem. GET /subscriptions and GET /subscriptions/{id}/charges have no paging fields. The charge list has no count. Open question

Impact. A truncated list looks the same as a full list. A monthly subscription grows its history forever.

Proposal. Cursor pagination with a documented default and maximum.

{ "subscriptionId": "sub_test_example", "items": [], "hasMore": true, "nextCursor": "chg_test_example_51" }

16. merchantOrgNr on reads

Problem. The payment link create response does not echo merchantOrgNr. Subscription reads never return it. Only GET /pay/{id} and the subscription create response show it.

Impact. Integrators cannot check which company a payment or subscription pays out to. They must keep their own copy and trust it.

Proposal. Return merchantOrgNr, merchantName and a KYC state on every read of a payment, link, subscription and charge.

{ "merchantOrgNr": "999999999", "merchantName": "Acme Gym AS", "merchantKycStatus": "pending" }

Payment methods

13. Card setup webhooks and failure reason

Problem. Card setup sends no webhook. failureReason is null even for a real refusal. Verified

Impact. Integrators poll after the customer returns, and cannot say why a card was rejected.

Proposal. Send payment_method.activated and payment_method.failed. Fill failureReason with the Adyen refusal. Consider payment_method.expiring one month before the card expires.

{
  "type": "payment_method.failed",
  "data": { "paymentMethodId": "pm_test_example", "shopperReference": "acme-member-001", "status": "failed", "failureReason": "Refused", "refusalCategory": "do_not_honor" }
}

Webhooks

3. Webhook redelivery and replay

Problem. Stated by Plorea A failed delivery is not retried. A deploy, a timeout or a 500 loses the event for good. Webhook URLs are registered manually, per tenant.

Impact. Integrators must poll everything as if webhooks did not exist. Webhooks then add little value.

Proposal.

  • Retry non-2xx deliveries with exponential backoff for at least 24 hours.
  • An events endpoint to list and replay recent events.
  • An endpoint to register and update webhook URLs per environment.
{ "items": [ { "eventId": "evt_…", "type": "payment.failed", "createdAt": "…", "deliveryStatus": "failed", "attempts": 6 } ], "hasMore": false }
{ "eventId": "evt_…", "deliveryStatus": "queued" }

Testing

4. Sandbox failure triggers

Problem. A failed subscription charge cannot be produced in test. Adyen's decline triggers live on the payment request, and Plorea's scheduler builds that request server-side. Not observable in test

Impact. Dunning code ships untested against real shapes: the 402 body, payment_failed, retryCount and failed charge items.

Proposal. Either of these works:

  • Pass Adyen's RequestedTestAcquirerResponseCode through on manual charges in test.
  • Mark a test subscription so its next scheduled charge declines.
{ "reason": "dunning test", "testResponseCode": "51" }
{ "testNextChargeOutcome": "refused" }

Platform

6. OpenAPI specification

Problem. No published contract exists. Integrators learn the shapes by trial, and by asking Plorea.

Impact. Each integrator repeats the same discovery. Client generation, mock servers and contract tests are not possible.

Proposal. Publish an OpenAPI 3.1 file at a stable URL, for example https://payments.plorea.no/openapi.json. These docs and their captured responses are a starting point, free to use.

17. Machine-readable error codes

Problem. Errors carry one English error string. The strings are static templates, and one message can list fields that are present.

Impact. Integrators can branch only on the HTTP status. Two different 400s look the same to code.

Proposal. Keep error for humans. Add a stable code, the failing field, and a request ID.

{
  "error": "Invalid merchantOrgNr — must be 9 digits",
  "code": "invalid_merchant_org_nr",
  "field": "merchantOrgNr",
  "requestId": "req_…"
}

Return the same requestId in a response header on every call. Support can then find a call in seconds.

18. Changelog and versioning

Problem. Behaviour changes without notice. In September 2026, session endpoints changed three times in four days. Each change was an improvement, but integrators found out by probing.

Impact. Integrators cannot plan releases. A breaking change can reach production unnoticed.

Proposal.

  • A public changelog page with dates.
  • A version header, for example Plorea-Version: 2026-10-01, so integrators opt in to breaking changes.
  • A notice period for breaking changes, sent by email to integrators.
  • A status page for incidents.

Smaller items

  • Consistent spelling. Payments use cancelled, subscriptions use canceled. Pick one, or document both.
  • Consistent metadata. An empty metadata returns [], not {}. Return an object.
  • Environment default. A missing X-Environment on refund uses live credentials. Reject a request with no header, or default to test everywhere.
  • Native 3-D Secure. Promised by Plorea Request native 3DS2 on iOS and Android sessions.
  • KYC visibility. An endpoint to start or read KYC for an organisation number, instead of a self-paid payment link.
