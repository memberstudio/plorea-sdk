Payments

Embedded and native checkout

The hosted pay page is Adyen Drop-in on a session. You can open the same kind of session yourself and mount Drop-in on your own web page or in a native iOS or Android app. The customer then pays without leaving your product.

If you only need a payment inside an app, a WebView on the hosted page is the cheapest option. Choose Drop-in when you want the checkout to look and feel like your product.

How it fits together

The browser or app never talks to Plorea. Your API key stays on your server. The server opens the session and passes four values to the client. Drop-in then talks to Adyen directly.

Before you start: what to ask Plorea for

  1. Your web origins whitelisted.List every domain that mounts Drop-in. Adyen checks the browser's Origin against the client key. An origin that is not on the list fails late, in Drop-in's /sessions/{id}/setup call, as a CORS or 403 error that looks like a credentials problem.
  2. Your app identifiers registered.The iOS bundle id with the Apple Team ID, and the Android package name. Include staging builds. Adyen does not check them on app calls today, so a missing id blocks nothing. Register them before go-live anyway. Stated by Plorea
  3. Optionally, a client key for each environment.Every session response now carries a clientKey, so you rarely need your own. Keep one as a fallback only.

Origin whitelisting rules

  • Per key, browsers only. The allow-list belongs to a client key. Adyen checks it only when the caller sends an Origin header. A native SDK sends none, so native apps pass with any valid key. Verified
  • Wildcards cover subdomains, not the bare domain. https://*.example.com covers pay.example.com and a.b.example.com. It does not cover https://example.com. Ask for the bare domain separately. Verified
  • No localhost. localhost is not whitelisted. Develop against a whitelisted staging subdomain, or use a tunnel on such a subdomain. Verified
  • Use the key from the session. The hosted pay page uses its own key, registered only for pay.plorea.no. That key answers 403 from your origin. The key in the session response is the one registered for your origins. Verified
  • Customers' own domains. Every domain needs a manual whitelist entry, and no API for this is planned. Serve the payment step from a wildcard subdomain you control, for example {customer}.example.com. Stated by Plorea

Create a checkout session

POST/payments/session

The session derives everything (amount, currency, merchant, reference) from the payment link. Create the link first. See Payment links.

use MemberFlow\Plorea\Enums\Channel;
use MemberFlow\Plorea\Facades\Plorea;

public function store(Request $request, Invoice $invoice)
{
    $this->authorize('pay', $invoice);

    $channel = Channel::from($request->validate([
        'channel' => ['required', Rule::enum(Channel::class)],
    ])['channel']);

    $link = Plorea::payments()
        ->link($invoice->reference, $invoice->title, $invoice->amount(), route('invoices.paid', $invoice))
        ->merchant(orgNr: '999999999', name: 'Acme Gym AS')
        ->firstOrCreate();

    $session = Plorea::payByLink()->session(
        $link->id,
        returnUrl: $this->returnUrlFor($channel, $invoice),  // chosen on the server
        channel: $channel,
    );

    // Serialises to sessionId, sessionData, clientKey, environment — nothing else.
    return response()->json($session);
}

Good server habits

  • Pass on only four fields. Do not forward the whole response. Keep tenant and customer data on the server.
  • One session per attempt. Sessions expire. Do not cache them. Reuse the link, not the session.
  • Choose returnUrl on the server. Never take it from the request. That is an open redirect.
  • Authorise the caller. Check that the user may pay this invoice before you open a session.

Web: mount Drop-in

The examples use Adyen Web v6. Load Adyen's script and stylesheet, then mount Drop-in on a container element.

const { AdyenCheckout, Dropin } = window.AdyenWeb;

const session = await fetch(`/api/invoices/${invoiceId}/checkout`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'X-CSRF-TOKEN': csrfToken },
  body: JSON.stringify({ channel: 'Web' }),
}).then((r) => r.json());

const checkout = await AdyenCheckout({
  clientKey: session.clientKey,
  environment: session.environment, // "test" or "live"
  countryCode: 'NO',
  locale: 'nb-NO',
  session: { id: session.sessionId, sessionData: session.sessionData },
  // These are UI hints only. The server decides whether the invoice is paid.
  onPaymentCompleted: () => location.assign(`/invoices/${invoiceId}/paid`),
  onPaymentFailed: () => showRetry(),
  onError: (error) => reportError(error),
});

new Dropin(checkout).mount('#checkout');

Finish a redirect payment

3-D Secure and redirect methods leave your page. The customer returns to returnUrl with sessionId and redirectResult in the query string. Finish the payment there:

const params = new URLSearchParams(location.search);

const checkout = await AdyenCheckout({
  clientKey,             // from your server, as before
  environment,
  session: { id: params.get('sessionId') },
  onPaymentCompleted: () => showProcessing(),
  onPaymentFailed: () => showRetry(),
});

checkout.submitDetails({ details: { redirectResult: params.get('redirectResult') } });

Content Security Policy

Drop-in loads from and connects to Adyen's checkoutshopper-*.adyen.com hosts. 3-D Secure opens an iframe to the card issuer. A strict CSP needs script-src, style-src, connect-src and frame-src entries for these. Use Adyen's CSP guide for the current host list.

3-D Secure arrives as a browser redirect

Plorea's sessions do not ask for native 3DS2 today. A 3-D Secure challenge opens in a browser and returns through returnUrl. Verified on iOS So the return-URL handling is on the critical path for card payments in your app. Plorea plans to enable native 3DS2 on iOS and Android sessions. Stated by Plorea

Return URLs for apps

  • Universal links (iOS) and App Links (Android) are the recommended choice. They need apple-app-site-association and assetlinks.json on your domain.
  • A custom scheme such as acmeapp://payment/return is accepted on both session endpoints. Verified An earlier version of the API rejected it with 400 "returnUrl must be a valid http(s) URL". If you see that error, report it to Plorea.

Confirm the result on the server

onPaymentCompleted and the native result callbacks are hints for the UI. They are not proof of payment.

  1. The client says "done".Your server reads GET /payments/status/{reference} and answers with the real state.
  2. The webhook pushes the result.payment.authorised or payment.failed arrives a few seconds after the decision. Use it to update a customer who closed the app. See Webhooks.
  3. Book idempotently.The webhook, the poll and the return page can race. Key the booking on the reference.
  4. Time out abandoned sessions yourself.A session that the customer closes stays created forever. Nothing marks it failed. Verified Stop waiting after a timeout you choose, and open a new session for the next try.

Storing a card with Drop-in

Card setup has its own session endpoint, POST /payment-methods/setup/session. It takes the same channel values and returns a clientKey for every channel. It differs in one important way: there is no webhook for card setup, so you must poll the payment method. See Storing cards.

Wallets and app store rules

  • Apple Pay and Google Pay show only when Plorea's Adyen account is set up for them. Apple Pay on the web needs Apple's domain-association file on every domain. Apple Pay in an app needs an Apple merchant id and certificate. Ask Plorea which wallets it offers before you promise them. Open question
  • App stores. Apple and Google require in-app purchase for digital goods used inside the app. Physical goods and real-world services, such as a gym membership or an invoice, are generally exempt. Check the current store rules for your case.
