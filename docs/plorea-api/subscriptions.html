Recurring billing

Subscriptions

A subscription charges a stored card a fixed amount on a fixed interval. Plorea runs the scheduler. Your app creates the subscription, reacts to its state and grants access. Your app never starts the recurring charge.

Plorea owns the schedule

This is the most important rule on this page. Plorea decides when to charge, charges, and moves nextChargeAt forward. Your app reads the result. If your app also charges on a schedule, the customer pays twice.

Before you start

  • An active payment method with recurringType: "Subscription". See Storing cards.
  • A place in your database to store subscriptionId, externalId and, if you bill for other companies, merchantOrgNr.
  • A webhook endpoint for subscription.charge_succeeded, and a scheduled job that polls. See Webhooks and Failed charges and dunning.

The lifecycle

StatusMeaningGrant access?Source
trialingIn a free trial. Nothing is charged until trialEndsAt.YesVerified
activeBilling on schedule.YesVerified
canceledNo more charges. Spelled the US way, with one L.Until accessEndsAtVerified
payment_failedA scheduled charge failed. Retries may follow.Your decisionNot observable in test

trialing is not a kind of active

The two statuses are separate. Grant access when the status is trialing or active. A check for active alone locks out every customer in a trial.

Billing timeline

Billing starts immediately. The create response already holds the first nextChargeAt. Without a trial, the scheduler charges the card within seconds. Verified

After each successful charge, Plorea sets lastChargeAt and moves nextChargeAt forward by one interval. There is no option to start billing on a fixed day, such as the 1st of the month. To get that effect, set a trial that ends on that day.

async function plorea(method, path, body) {
  const res = await fetch(`https://payments.plorea.no/${path}`, {
    method,
    headers: {
      Authorization: `Bearer ${process.env.PLOREA_API_KEY}`,
      'X-Environment': 'test',
      'Content-Type': 'application/json',
      Accept: 'application/json',
    },
    body: body ? JSON.stringify({ platform: 'acme', ...body }) : undefined,
  });
  const json = await res.json();
  if (!res.ok) throw Object.assign(new Error(json.error), { status: res.status, body: json });
  return json;
}

Create is not safe to retry

Plorea has no idempotency key. If a create call times out and you send it again, you can get two subscriptions that both bill the card. Before you retry, list subscriptions by externalId and check if the first call succeeded. Verified for payment links. See Errors and retries.

Route the money to a company

A platform that bills for many companies names the receiving company on each subscription. Send the company's nine-digit organisation number as merchantOrgNr. Every charge on the subscription, scheduled or manual, then settles to that company. Stated by Plorea

  -H "Authorization: Bearer $PLOREA_API_KEY" \
  -H "X-Environment: test" \
  -H "Content-Type: application/json" \
  -d '{
    "platform": "acme",
    "tenantId": "acme-platform",
    "paymentMethodId": "pm_test_golden_method",
    "recurringType": "Subscription",
    "amount": { "value": 49900, "currency": "NOK" },
    "interval": { "unit": "month", "count": 1 },
    "externalId": "membership-458",
    "merchantOrgNr": "999999999",
    "merchantName": "Acme Gym AS",
    "merchantEmail": "billing@example.com"
  }'
$subscription = Plorea::subscriptions()
    ->create($methodId, Amount::nok(49900), BillingInterval::monthly())

    ->save();

// Only the create response carries it. Store it now.
$membership->update(['merchant_org_nr' => $subscription->merchantOrgNr]);

  • The create response echoes merchantOrgNr as its last key. It does not echo the name or email. Verified
  • Reads, lists and charge history do not return merchantOrgNr. Store it in your own database when you create the subscription. Verified
  • A value that is not nine digits returns 400 "Invalid merchantOrgNr — must be 9 digits". Verified
  • Use the client company's number, never your platform's own number.
  • KYC for a new company starts on its first charge. Settlement splits apply from that charge. Charge webhooks carry the organisation number. Stated by Plorea
  • There is no API to start or read KYC. To onboard a company before its first real charge, create a payment link with its organisation number and pay it yourself. Stated by Plorea

Update a subscription

PATCH/subscriptions/{subscriptionId}

Send only the fields you want to change. Allowed fields:

  • amount, quantity, vatRate, vatAmount — the price.
  • paymentMethodId — a new active card. Any other status returns 400.
  • externalId, title, description — your labels.

You cannot change interval, trialEndsAt, nextChargeAt or merchantOrgNr. To change the interval, cancel and create a new subscription. See Subscription workflows.

Update VAT together with the amount

vatAmount is an absolute number of øre. Plorea does not recalculate it when the amount changes. If you change the price, send the new vatAmount in the same request.

An amount change applies to the next scheduled charge. That is the expected behaviour, but we have not watched a renewal after a price change. Open question Plorea does not prorate.

Charge is not safe to retry

A second call creates a second charge. If a charge call times out, read the charge history before you try again.

Charge references

Each charge has a payment reference in the format {subscriptionId}-{chargeId}, for example sub_test_golden-chg_test_golden_1. The subscription shows the latest one as lastPaymentReference.

Cancel

POST/subscriptions/{subscriptionId}/cancel

Cancel stops future charges. It does not refund anything. The customer keeps access until the end of the period they paid for.

curl -X POST https://payments.plorea.no/subscriptions/sub_test_golden/cancel \
  -H "Authorization: Bearer $PLOREA_API_KEY" \
  -H "X-Environment: test" \
  -H "Content-Type: application/json" \
  -d '{ "platform": "acme", "reason": "customer_requested" }'
$cancellation = Plorea::subscriptions()->cancel('sub_test_golden', 'customer_requested');

// Null during a trial: access ends now.
$accessEndsAt = $cancellation->accessEndsAt ?? now();

$membership->update(['access_ends_at' => $accessEndsAt]);
const cancellation = await plorea('POST', 'subscriptions/sub_test_golden/cancel', {
  reason: 'customer_requested',
});

// Null during a trial: access ends now.
const accessEndsAt = cancellation.accessEndsAt ?? new Date().toISOString();
{
  "subscriptionId": "sub_test_golden",
  "status": "canceled",
  "canceledAt": "2026-09-04T10:04:00.000Z",
  "accessEndsAt": "2026-09-05T09:55:00.000Z",
  "reason": "customer_requested"
}

After cancel:

  • status is canceled and nextChargeAt is null.
  • accessEndsAt is the last charge plus one interval. In the example, the last charge was at 09:55 on a daily plan, so access ends at 09:55 the next day. Verified
  • The full object shows the reason as cancelReason. The cancel response calls it reason.
  • Plorea sends no webhook for a cancel. Stated by Plorea

A cancel during a trial returns accessEndsAt null

Plorea computes accessEndsAt from the last charge. A trial has no charge, so the value is null. Null means "access ends now". It does not mean "access never ends". If you store null as "no end date", a cancelled trial user keeps access forever. Verified

{
  "subscriptionId": "sub_test_golden_trial",
  "status": "canceled",
  "canceledAt": "2026-09-07T19:57:00.000Z",
  "accessEndsAt": null,
  "reason": "customer_requested"
}

Gate access on accessEndsAt, not on canceledAt and not on the status alone.

Reactivate

POST/subscriptions/{subscriptionId}/reactivate

Reactivate undoes a cancel. It takes no body. The subscription becomes active again, with the same price, card and interval.

curl -X POST https://payments.plorea.no/subscriptions/sub_test_golden/reactivate \
  -H "Authorization: Bearer $PLOREA_API_KEY" \
  -H "X-Environment: test" \
  -H "Content-Type: application/json" \
  -d '{ "platform": "acme" }'
$subscription = Plorea::subscriptions()->find($id);

if ($subscription->isCanceled()) {
    $subscription = Plorea::subscriptions()->reactivate($id);
}
const current = await plorea('GET', `subscriptions/${id}?platform=acme`);
if (current.status === 'canceled') {
  await plorea('POST', `subscriptions/${id}/reactivate`, {});
}
{
  "subscriptionId": "sub_test_golden",
  "tenantId": "test-tenant",
  "status": "active",
  "nextChargeAt": "2026-09-04T10:04:00.000Z",
  "reactivatedAt": "2026-09-04T10:04:00.000Z",
  "paymentMethodId": "pm_test_golden_method",
  "amount": { "value": 29900, "currency": "NOK" },
  "interval": { "count": 1, "unit": "day" },
  "externalId": "GOLDEN-EXT-001",
  "title": "Golden fixture plan"
}
  • Reactivate sets nextChargeAt to one interval after the last charge. It does not charge again for a period the customer already paid. Verified
  • If that time is already in the past, the scheduler charges soon after reactivation. Tell the customer before you reactivate a long-cancelled subscription.
  • Reactivating a subscription that is not canceled returns 400. Verified
  • Plorea sends no webhook for a reactivate. Stated by Plorea
{
  "error": "Only canceled subscriptions can be reactivated",
  "status": "active"
}

History: reactivate used to double-bill

An earlier version of reactivate charged the card at once, even inside a paid period. Plorea fixed this. We verified the fix in test in September 2026. Production is not observed. A cheap guard: if accessEndsAt is still in the future, the customer still has access, and you may not need to reactivate yet.

Know when a renewal succeeds

Use two signals together.

  1. WebhookA scheduled charge sends subscription.charge_succeeded with subscriptionId, externalId, amount and the new nextChargeAt. Extend access to nextChargeAt. A manual charge sends payment.authorised instead. Verified
  2. PollingPlorea does not redeliver failed webhooks, and sends nothing for a failed charge. Run a scheduled job that reads each subscription. If nextChargeAt is more than an hour in the past and the status is not canceled, the renewal did not complete. See Failed charges and dunning.
use MemberFlow\Plorea\Events\SubscriptionChargeSucceeded;

Event::listen(SubscriptionChargeSucceeded::class, function ($event) {
    $subscription = Plorea::subscriptions()->find($event->subscriptionId);

    Membership::where('plorea_subscription_id', $subscription->id)
        ->first()
        ?->extendAccessTo($subscription->nextChargeAt); // idempotent
});

// Hourly: subscriptions that are overdue or report payment_failed.
foreach (Plorea::subscriptions()->needingAttention('membership-456') as $subscription) {
    // Ask the customer for a new card.
}
// In your webhook handler, after you verify the signature.
if (event.type === 'subscription.charge_succeeded') {
  await db.memberships.extendAccess(event.data.externalId, event.data.nextChargeAt);
}

// Hourly job.
const sub = await plorea('GET', `subscriptions/${id}?platform=acme`);
const overdue = sub.status !== 'canceled'
  && sub.nextChargeAt
  && Date.parse(sub.nextChargeAt) + 3600e3 < Date.now();
