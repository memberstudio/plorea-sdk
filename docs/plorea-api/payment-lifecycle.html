Payments

Payment lifecycle and states

A payment moves through a small set of statuses. This page lists each one, shows how they connect, and explains the two decisions that cause most bugs: when a payment counts as paid, and whether to cancel or refund.

Short version

  • authorised or paid means money moved. Book the order.
  • failed means the card was declined. There is no refused status.
  • Capture happens automatically. There is no capture call.
  • A link never reports expired. Check expiresAt yourself.
  • refund_requested means accepted. It can stay that way for many hours.

Authorisation and capture

A card payment has two steps. Authorisation reserves the amount on the card. Capture tells the card network to move the reserved money. Many gateways let you capture later, for example when you ship.

Plorea captures for you. Capture runs through AmendoPOS, usually within minutes of the authorisation. There is no capture endpoint and no "authorised, waiting for capture" state that you control. Stated by Plorea A manual capture endpoint is on Plorea's roadmap. Stated by Plorea

This has three effects on your code:

  1. authorised is your success state. Book the order on it. Do not wait for paid. In test, a payment never leaves authorised.
  2. You cannot hold an authorisation. Do not authorise now and charge "on shipment". Create the link when you are ready to take the money.
  3. The cancel window is short. Cancel works only until capture. After a few minutes, a refund is the safe choice.

What we need from Plorea

A captured status or a payment.captured webhook, so that integrators know when cancel stops working. Proposal See Gaps and proposals.

Cancel or refund?

Both undo a payment. They differ in what the customer sees and in when they work.

Use this rule. Capture is automatic and you cannot see when it runs, so:

  • Within a few minutes of authorisation and for the full amount: cancel.
  • Later, or for part of the amount: refund.
  • When in doubt: refund.

Waiting for a refund to settle

The status changes to refund_requested at once. Settlement is asynchronous. One test refund took more than 11 hours. Another refund and a cancel still showed the requested status after 24 hours. Verified Plorea says this is expected and that the final statuses are refunded and cancelled. Stated by Plorea

  • Book the refund when Plorea accepts it. Do not wait for refunded.
  • Never time out a refund. A job that gives up after one hour reports healthy refunds as failed.
  • Keep the refund response. refundPspReference appears only there. The status body has lastRefundRequestPspReference, which identifies the request. Verified
  • One refund at a time is visible. The status body has only lastRefund* fields. There is no per-refund status. Keep your own list of refunds. Verified

Expiry

Every link has an expiresAt in the create response. After that time the hosted page refuses payment. The status endpoint does not show this: an expired link keeps reporting created, and the response has no expiry field. Verified

Use one of two sources for expiry:

  1. The expiresAt you stored when you created the link. Compare it with the current time.
  2. The expired flag on GET /pay/{paymentLinkId}. Plorea computes it. This is the authoritative answer.
{
  "id": "pl_test_example",
  "reference": "ORDER-1001",
  "amount": 10000,
  "currency": "NOK",
  "expiresAt": "2099-12-31T12:00:00.000Z",
  "expired": false
}

An embedded checkout session has no terminal state either. An abandoned session reads created for hours. Time it out in your own code and open a new session for the next try. Verified

Declines

A declined card sets status to failed. Two more fields confirm it: webhookEventCode is AUTHORISATION and webhookSuccess is false. Verified

{
  "reference": "ORDER-1003",
  "status": "failed",
  "pspReference": "TESTPSPREF000009",
  "amount": 10000,
  "currency": "NOK",
  "webhookEventCode": "AUTHORISATION",
  "webhookSuccess": false,
  "lastWebhookAt": "2026-09-09T08:56:40.892Z"
}

The webhook* fields are about Adyen, not about you

webhookEventCode, webhookSuccess and lastWebhookAt describe the notification that Adyen sent to Plorea. They say nothing about the webhook that Plorea sends to you. After a refund, webhookEventCode still reads AUTHORISATION. Verified

The API gives no reason for a decline. You cannot tell "insufficient funds" from "card blocked". Show the customer a general message and offer a new attempt. Plorea says a refusalReason field is coming. Stated by Plorea Do not depend on it until you see it.

Is failed final for a link? The customer can probably try again on the same page, but this is not confirmed. Open question The safe pattern: on failed, create a new link on a suffixed reference for the next attempt.

How to decide "paid" in code

Three events can tell you about a payment: the customer returns, a webhook arrives, or your poll runs. They can arrive in any order, more than once, or not at all. Route all three into one function that re-reads the status and applies it idempotently.

use MemberFlow\Plorea\Exceptions\NotFoundException;
use MemberFlow\Plorea\Facades\Plorea;

function syncPayment(Order $order): void
{
    try {
        $status = Plorea::payments()->status($order->reference);
    } catch (NotFoundException) {
        return; // no link was created for this reference
    }

    match (true) {
        $status->isPaid() => $status->amount?->value === $order->amount_ore
            ? $order->markPaidOnce($status->pspReference)
            : $order->flagForReview('amount mismatch'),
        $status->isOpen() => $order->expires_at?->isPast() ? $order->markExpired() : null,
        $status->is('failed') => $order->markDeclined(),
        $status->isRefundRequested(), $status->is('refunded') => $order->markRefunded(),
        $status->isCancelRequested(), $status->is('cancelled') => $order->markCancelled(),
        default => $order->flagForReview("unknown status {$status->status}"),
    };
}
const OPEN = ['created', 'pending', 'active'];
const PAID = ['authorised', 'paid'];

export async function syncPayment(order) {
  const res = await fetch(
    `https://payments.plorea.no/payments/status/${encodeURIComponent(order.reference)}?platform=acme`,
    { headers: { Authorization: `Bearer ${process.env.PLOREA_API_KEY}`, 'X-Environment': 'test' } },
  );
  if (res.status === 404) return; // no link for this reference
  if (!res.ok) throw new Error(`Plorea ${res.status}`);

  const p = await res.json();
  const status = (p.status ?? '').toLowerCase();

  if (PAID.includes(status)) {
    if (p.amount === order.amountOre && p.currency === 'NOK') return order.markPaidOnce(p.pspReference);
    return order.flagForReview('amount mismatch');
  }
  if (OPEN.includes(status)) return new Date(order.expiresAt) < new Date() ? order.markExpired() : undefined;
  if (status === 'failed') return order.markDeclined();
  if (['refund_requested', 'refunded'].includes(status)) return order.markRefunded();
  if (['cancel_requested', 'cancelled'].includes(status)) return order.markCancelled();
  return order.flagForReview(`unknown status ${p.status}`);
}

Rules that keep the books right

  • Mark paid once. Use a database constraint or a conditional update. The webhook and the poll can run at the same moment.
  • Check the amount. Compare amount and currency with your order before you book.
  • Poll open payments on a schedule. Plorea does not redeliver a failed webhook. Stated by Plorea Poll every few minutes for the first hour, then less often until expiresAt.
  • Stop polling at a final state. Stop at failed, refunded and cancelled, and at expiry. For the requested states, poll on a scale of hours.
  • Never create a second link for a paid order. Read the status before every create. A duplicate link is payable. Verified
