Recurring billing

Failed charges and dunning

Dunning is the process of recovering a renewal that the bank declined: you detect the failure, tell the customer, get a working card, and collect the money. On Plorea, the detection step needs extra care, because a failed renewal sends no webhook.

A failed renewal is silent

Plorea sends no webhook when a scheduled charge fails. Stated by Plorea If you only listen for webhooks, a declined renewal looks exactly like "nothing happened". You must poll. This page shows how.

Two kinds of failure

A subscription can fail to charge in two places. They behave differently and need different handling.

What is known

No failed subscription charge has ever been observed in the test environment. This is not for lack of trying. Adyen's test cards decline only through fields on the payment request. For a stored card, that request is the card setup. A card that declines therefore fails the setup and is never stored. No test card stores successfully and then declines later. Not observable in test

So the failure shapes below come from Plorea's description, not from a response we have seen. Write code that tolerates small differences.

402 Payment Required on a manual charge
Means the card was declined. Nothing else returns 402. A canceled subscription or an inactive card returns 400 instead. Stated by Plorea for 402, Verified for 400.
retryPolicy {maxRetries, retryIntervalDays}
Set on create. After a declined renewal the scheduler tries again every retryIntervalDays days, up to maxRetries times. Stated by Plorea The exact timing and what happens after the last retry have not been observed. Open question
status: "payment_failed"
The subscription status after a failed renewal, according to Plorea. Never observed. Not observable in test
retryCount, failureReason on the subscription
Fields exist in every read. retryCount has always been 0 and failureReason always null. Verified for the shape. Their values after a failure are unknown.
retryNumber, failureReason on a charge
Fields exist on each item of GET /subscriptions/{id}/charges. Whether a failed attempt appears there as its own item is unknown. Open question
No reason codes
failureReason is null even for a genuine refusal on a card setup. Verified Do not branch on it. Branch on status.

Detect failures by polling

The scheduler charges within seconds of nextChargeAt and then moves nextChargeAt forward by one interval. Verified This gives a reliable test that does not depend on any failure field:

The overdue rule

An active subscription whose nextChargeAt is more than a grace period in the past did not complete its cycle. Something went wrong: a decline, a retry in progress, or a stuck scheduler. A canceled subscription is never overdue: it keeps its old nextChargeAt.

Flag a subscription for attention when either test is true:

TestBasis
status is payment_failedPlorea's description. Never observed. Not observable in test
status is not canceled, and nextChargeAt + grace < nowFields observed on the wire. Carries the weight. Verified
  1. Schedule a jobRun it at least as often as your shortest grace period. Hourly suits monthly plans.
  2. List subscriptions per billed entityCall GET /subscriptions?externalId=… or ?tenantId=…. The list has never been seen to paginate. If you hold many subscriptions per filter, compare count with your own records. Open question
  3. Apply the two testsKeep the subscriptions that are payment_failed or overdue.
  4. Read the charge historyCall GET /subscriptions/{id}/charges. The newest item comes first.
  5. DecideIf the newest charge is not authorised, or no charge covers the missed date, start dunning.

// needingAttention() = payment_failed OR nextChargeAt older than graceMinutes.

foreach ($flagged as $subscription) {
    $latest = Plorea::subscriptions()->charges($subscription->id)->first();

    if ($latest?->isAuthorised() !== true) {
        // Start dunning. Do not branch on failureReason: it is null.
        StartDunning::dispatch($subscription->id);
    }
}

Choose a grace period

The grace period absorbs scheduler lag. Observed lag between nextChargeAt and the charge was from seconds to about 4.5 minutes. Verified 60 minutes is a safe default. Use a shorter value for daily plans. Do not use a value shorter than your job interval.

Also use the success webhook

subscription.charge_succeeded arrives for each successful renewal. Verified Use it to extend access and to close an open dunning case early. Do not use the absence of this webhook as the failure signal: failed deliveries are not redelivered, so a missing webhook can also mean a lost delivery. Stated by Plorea

The dunning sequence

Plorea's retries and your messages to the customer run side by side. The example uses retryPolicy: { maxRetries: 3, retryIntervalDays: 1 }.

  1. Open a dunning caseStore the subscription ID, the missed nextChargeAt and the time you first flagged it. Use the case to avoid sending the same email twice.
  2. Notify the customer at onceSay that the payment failed, the amount, and how long access continues. Link to a card update page. Do not guess the reason: the API does not give one.
  3. Keep access for a grace periodMost declines are temporary: low balance, a blocked card, an expired card. A grace period of 3–7 days keeps good customers.
  4. Collect a new cardRun Replace the card: a new setup, then PATCH paymentMethodId.
  5. Collect the missed amountSee Collect the missed renewal.
  6. Close or escalateWhen a charge succeeds, close the case. When your grace period ends, suspend access. When you give up, cancel the subscription.

Collect the missed renewal

After the customer adds a new card, you must decide whether to charge now or to wait for Plorea's next retry. The API does not tell you which retry is pending.

Risk of a double charge

If you charge manually and Plorea's scheduler then also retries the missed renewal, the customer pays twice. Whether a manual charge stops the pending retries is unknown. Open question

  1. PATCH the new card firstA retry can only succeed on a working card. Whether pending retries use the card stored at retry time is not confirmed. Open question
  2. Re-read the subscription and the chargesCheck whether a retry already succeeded.
  3. Charge now only if no retry is leftIf the subscription is still overdue after the last retry window, call POST /subscriptions/{id}/charge without an amount. The subscription amount is used. Use reason: "dunning_recovery".
  4. Handle 402 and 400402 means the new card also declined. 400 means the subscription is canceled or the card is not active.
  5. Re-read nextChargeAtConfirm the schedule moved forward. If it did not, the subscription stays overdue and your job flags it again.
curl -X POST https://payments.plorea.no/subscriptions/sub_test_acme_001/charge \
  -H "Authorization: Bearer $PLOREA_API_KEY" \
  -H "X-Environment: test" \
  -H "Content-Type: application/json" \
  -d '{ "platform": "acme", "reason": "dunning_recovery" }'
use MemberFlow\Plorea\Exceptions\ChargeFailedException;
use MemberFlow\Plorea\Exceptions\ValidationException;
use MemberFlow\Plorea\Facades\Plorea;

$subscriptions = Plorea::subscriptions();
$subscription = $subscriptions->find('sub_test_acme_001');

if (! $subscription->isOverdue() && ! $subscription->hasPaymentFailure()) {
    $case->close(); // A retry already succeeded.
    return;
}

try {
    $charge = $subscriptions->charge($subscription->id, reason: 'dunning_recovery');
    $case->close($charge->reference);
} catch (ChargeFailedException $e) {
    // 402: the new card declined too. Keep the case open.
} catch (ValidationException $e) {
    // 400: canceled, or the card is not active. Fix state first.
}
const res = await fetch(`${base}/subscriptions/sub_test_acme_001/charge`, {
  method: 'POST',
  headers: { ...headers, 'Content-Type': 'application/json' },
  body: JSON.stringify({ platform: 'acme', reason: 'dunning_recovery' }),
});

if (res.status === 402) {
  // Declined again. Keep the case open.
} else if (res.status === 400) {
  // Not chargeable. Check status and card.
} else if (res.ok) {
  const charge = await res.json(); // status "charge_created", resultCode
}

Give up and cancel

When dunning fails, cancel the subscription with a clear reason, for example "payment_failed". Read accessEndsAt. It is based on the last successful charge, so after a missed renewal it is usually in the past. Verified for the formula. Remove access at once in that case.

$cancellation = Plorea::subscriptions()->cancel('sub_test_acme_001', 'payment_failed');

$endsAt = $cancellation->accessEndsAt ?? now();
$member->update(['access_ends_at' => $endsAt->min(now())]);

Testing your dunning code

You cannot produce a failed renewal in the Plorea test environment. Not observable in test Test with stubs instead:

  • Stub a subscription read with nextChargeAt in the past and status: "active". This is the case that will actually happen.
  • Stub a subscription with status: "payment_failed", a non-zero retryCount and a null failureReason.
  • Stub a charge call that returns 402 with {"error": "…"}. Do not assert on the message text.
  • With the PHP SDK, use Plorea::fake() and pass a fixed clock to isOverdue().

What we need from Plorea

Dunning is the weakest part of the API today. These changes would make it reliable. See Gaps and proposals for the full list.
