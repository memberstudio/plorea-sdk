Recurring billing

Failed charges and dunning

Dunning is the process of recovering a renewal that the bank declined: you detect the failure, tell the customer, get a working card, and collect the money. On Plorea, the detection step needs extra care, because the failure webhook is new, unofficial and never redelivered.

Do not rely on the failure webhook alone

A failed scheduled charge moves the subscription to past_due. Verified in production. In test, Plorea also sent a subscription.charge_failed webhook. Verified in test. That event is not in Plorea's catalogue, none arrived for the production failure, and a failed delivery is never redelivered. You must poll as well. This page shows how.

A subscription can fail to charge in two places. They behave differently and need different handling.

What is known

One failed scheduled charge was captured in production on 2026-10-01, and one full retry sequence on 6 to 8 October 2026. The stored card could no longer be found by the provider. In test, the same cause produced the subscription.charge_failed webhook three times. A real decline has not been observed. Adyen's test cards decline only through fields on the payment request. For a stored card, that request is the card setup, so a declining card is never stored. Not observable in test

Write code that tolerates small differences between a decline and the captured case.

Detect failures by polling

The scheduler charges within seconds to a few minutes of a natural nextChargeAt and then moves it forward by one interval. The overdue rule

An active subscription whose nextChargeAt is more than a grace period in the past did not complete its cycle. Something went wrong without a failure status, for example a stuck scheduler. A canceled or paused subscription is never overdue. A past_due one is not overdue either, because its nextChargeAt moved to the next retry.

Flag a subscription for attention when any test is true:

TestBasis
status is past_dueA failed charge that Plorea retries. Verified in production
status is payment_failedThe retries ran out. nextChargeAt is null, so the date test never flags it. Seen in production on 6 to 8 October 2026. Verified in production
status is not canceled or paused, and nextChargeAt + grace < nowA cycle that stalled without a failure status. Verified fields
  1. Schedule a jobRun it at least as often as your shortest grace period. Hourly suits monthly plans.
  2. List subscriptions per billed entityCall GET /subscriptions?externalId=… or ?tenantId=…. The list has never been seen to paginate. If you hold many subscriptions per filter, compare count with your own records. Open question
  3. Apply the testsKeep the subscriptions that are past_due, payment_failed or overdue.
  4. Start dunning for a failure statusA past_due subscription reports the failure itself. Do not compare dates: its nextChargeAt is the next retry, not the missed renewal.
  5. Read the charge history for an overdue oneCall GET /subscriptions/{id}/charges. The newest item comes first.
  6. DecideA charge covers the missed renewal only if it is authorised and its createdAt is on or after the missed nextChargeAt. An older success does not count. If no charge covers the missed renewal, start dunning.

use MemberFlow\Plorea\Facades\Plorea;

// Scheduled, e.g. hourly, once per billed entity.
// needingAttention() = past_due OR payment_failed OR nextChargeAt older than graceMinutes.
$flagged = Plorea::subscriptions()->needingAttention('member-1001', graceMinutes: 60);

foreach ($flagged as $subscription) {
    if ($subscription->isPastDue() || $subscription->hasPaymentFailure()) {
        // Plorea reports the failure. nextChargeAt is the next retry, not the miss.
        StartDunning::dispatch($subscription->id);
        continue;
    }

    // Overdue: the cycle stalled without a failure status.
    $missedAt = $subscription->nextChargeAt;
    $latest = Plorea::subscriptions()->charges($subscription->id)->first();

    // An older success must not hide the missed renewal.
    $covered = $latest?->isAuthorised() === true
        && $missedAt !== null
        && $latest->createdAt?->greaterThanOrEqualTo($missedAt) === true;

    if (! $covered) {
        StartDunning::dispatch($subscription->id);
    }
}

  if (failed(s)) {

  const latest = items[0];
  const covered =
    latest?.status === 'authorised' &&
    missedAt !== null &&
    new Date(latest.createdAt).getTime() >= missedAt;

  if (!covered) {
    await startDunning(s.subscriptionId);
  }
}

Choose a grace period

The grace period absorbs scheduler lag. Observed lag between nextChargeAt and the charge was from seconds to about 4.5 minutes. Verified 60 minutes is a safe default. Use a shorter value for daily plans. Do not use a value shorter than your job interval.

Use the webhooks as fast signals

subscription.charge_failed lets you open a dunning case at once. Verified in test. Treat it as a ping: fetch the subscription and read the history. Deduplicate on the body's eventId. Keep the polling job, because a lost delivery is never redelivered and a stalled cycle sends nothing.

use MemberFlow\Plorea\Events\SubscriptionChargeFailed;
use MemberFlow\Plorea\Facades\Plorea;

Event::listen(SubscriptionChargeFailed::class, function (SubscriptionChargeFailed $event) {
    $subscription = Plorea::subscriptions()->find($event->subscriptionId);

    if ($subscription->isPastDue() || $subscription->hasPaymentFailure()) {
        StartDunning::dispatch($subscription->id); // idempotent per subscription
    }
    // $event->failureReason is free text: show it, never branch on it.
});
// In your webhook handler, after you verify the signature.
if (event.type === 'subscription.charge_failed') {
  const s = await fetch(
    `${base}/subscriptions/${event.data.subscriptionId}?platform=acme`,
    { headers },
  ).then((r) => r.json());
  if (s.status === 'past_due' || s.status === 'payment_failed') {
    await startDunning(s.subscriptionId); // idempotent per subscription
  }
}

subscription.charge_succeeded arrives for each successful renewal. Verified Use it to extend access and to close an open dunning case early. Do not use the absence of this webhook as the failure signal: failed deliveries are not redelivered, so a missing webhook can also mean a lost delivery. Stated by Plorea

The dunning sequence

Plorea's retries and your messages to the customer run side by side. The example uses retryPolicy: { maxRetries: 3, retryIntervalDays: 1 }.

  1. Open a dunning caseStore the subscription ID, the missed nextChargeAt, the time you first flagged it and the end of the retry window. Use the case to avoid sending the same email twice.
  2. Notify the customer at onceSay that the payment failed, the amount, and how long access continues. Link to a card update page. Do not guess the reason: failureReason is the provider's free text, not a stable code.
  3. Keep access for a grace periodMost declines are temporary: low balance, a blocked card, an expired card. A grace period of 3–7 days keeps good customers.
  4. Collect a new cardRun Replace the card: a new setup, then PATCH paymentMethodId.
  5. Collect the missed amountSee Collect the missed renewal.
  6. Close or escalateWhen a charge succeeds, close the case. When your grace period ends, suspend access. When you give up, cancel the subscription.

After the last retry

In production on 6 to 8 October 2026, one subscription was tried three times, about 24 hours apart. Then it became payment_failed with retryCount: 3 and nextChargeAt: null. It was not canceled. Verified in production. Plorea has not confirmed this as a fixed policy. Open question

A retry charges the amount that the subscription holds when the retry runs. If you PATCH the amount during the retry window, the next retry uses the new amount. Stated by Plorea

Leaving payment_failed is untested

No route out of payment_failed has been tested. Do not assume that any call below returns the subscription to active.

RouteWhat we know
PATCH with a new amount and nextChargeAtNot tested on a payment_failed subscription. Changing both fields in one update is unverified on any status. Moving nextChargeAt on an active subscription has never produced a charge. Unobserved
PATCH status: "active" (resume)Verified only from paused. On an active subscription it returns 400 with allowedTransitions: ["paused"]. Not tested on payment_failed. Unobserved

Collect the missed renewal

After the customer adds a new card, you must decide whether to charge now or to wait for Plorea's next retry. The API does not tell you which retry is pending.

Risk of a double charge

If you charge manually and Plorea's scheduler then also retries the missed renewal, the customer pays twice. Whether a manual charge stops the pending retries is unknown. Open question

  1. PATCH the new card firstA retry can only succeed on a working card. Whether pending retries use the card stored at retry time is not confirmed. Open question
  2. Re-read the subscription and the chargesCheck whether a retry already succeeded.
  3. Wait until the retry window endsWhile the subscription is past_due, Plorea still retries and nextChargeAt is the next attempt. The API does not say when Plorea stops retrying. Elapsed time alone does not prove that Plorea stopped. Then re-read the subscription. Charge only when it reads payment_failed with nextChargeAt null.   4. Charge onceCall POST /subscriptions/{id}/charge without an amount. The subscription amount is used. Use reason: "dunning_recovery".
  5. Save the charge reference at onceStore it on the case before any other step. If the case already has a reference, do not charge again. Reconcile that charge instead.
  6. Handle 402 and 400402 means the new card also declined. 400 means the subscription is canceled or the card is not active.
  7. Confirm the outcome before you close the caseThe charge call returns status: "charge_created", not authorised. Read GET /subscriptions/{id}/charges and find the item with your reference. Close the case only when that item is authorised. Then confirm that nextChargeAt moved forward.

use MemberFlow\Plorea\Exceptions\ValidationException;
use MemberFlow\Plorea\Facades\Plorea;

use MemberFlow\Plorea\Data\SubscriptionCharge;

$subscriptions = Plorea::subscriptions();
$subscription = $subscriptions->find($case->subscription_id);

if (! $subscription->isPastDue()
    && ! $subscription->hasPaymentFailure()
    && ! $subscription->isOverdue()) {
    $case->close(); // The renewal completed.
    return;
}

if ($case->recovery_reference === null) {
    // retries_end_at = first flagged + maxRetries × retryIntervalDays + margin.
    if (now()->lt($case->retries_end_at)) {
        return; // Plorea may still retry. A charge now risks a double charge.
    }

    if (! $subscription->hasPaymentFailure() || $subscription->nextChargeAt !== null) {
        return; // Time alone does not prove the retries stopped.
    }

    try {
        $charge = $subscriptions->charge($subscription->id, reason: 'dunning_recovery');
    } catch (ChargeFailedException $e) {
        return; // 402: the new card declined too. Keep the case open.
    } catch (ValidationException $e) {
        return; // 400: canceled, or the card is not active. Fix state first.
    }

    // Save before any other step, so a crash cannot cause a second charge.
    $case->update(['recovery_reference' => $charge->reference]);
}

// "charge_created" is not "authorised". Confirm in the history.
$landed = $subscriptions->charges($subscription->id)
    ->first(fn (SubscriptionCharge $item): bool => $item->reference === $case->recovery_reference);

if ($landed?->isAuthorised() === true) {
    $case->close();
}
// Otherwise keep the case open. The next run reconciles the same charge.
const id = dunningCase.subscriptionId;

if (!dunningCase.recoveryReference) {

  if (res.status === 400) return; // Not chargeable. Check status and card.

  dunningCase.recoveryReference = charge.reference;

Give up and cancel

When dunning fails, cancel the subscription with a clear reason, for example "payment_failed". Read accessEndsAt. It is based on the last successful charge, so after a missed renewal it is usually in the past. Verified for the formula. Remove access at once in that case.

$cancellation = Plorea::subscriptions()->cancel('sub_test_acme_001', 'payment_failed');

$endsAt = $cancellation->accessEndsAt ?? now();
$member->update(['access_ends_at' => $endsAt->min(now())]);

Testing your dunning code

You cannot produce a declined renewal in the Plorea test environment. Not observable in test Test with stubs instead:

  • Stub a subscription read with status: "past_due", retryCount: 1, a text failureReason and a nextChargeAt in the future. This is the shape captured in production. Check that your job still flags it.
  • Stub a subscription.charge_failed delivery. Check that a duplicate eventId opens only one case.
  • Stub a subscription read with nextChargeAt in the past and status: "active": a stalled cycle.
  • Stub a subscription with status: "payment_failed", a non-zero retryCount and no failureReason. Plorea's documentation names this status, and production showed it once.
  • Stub a charge call that returns 402 with {"error": "…"}. Do not assert on the message text.
  • With the PHP SDK, use Plorea::fake() and pass a fixed clock to isOverdue().
