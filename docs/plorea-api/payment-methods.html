Recurring billing

Storing cards

A payment method is a stored card. You verify the card once while the customer is present. After that, you or Plorea's scheduler can charge it without the customer. Every subscription needs an active payment method.

Two objects, two lifecycles

A payment method and a subscription are separate objects. The payment method holds the card token. The subscription holds the price and the schedule. You create the payment method first. You can replace the card on a subscription later without touching the price or the schedule.

How card storage works

Plorea stores a card through Adyen. To prove that the card is real and that the customer agrees, Plorea makes a verification authorisation of 1 NOK. Adyen then returns a token for the card. Plorea keeps the token on the payment method as storedPaymentMethodId. Verified

The 1 NOK authorisation is not a charge. The customer is not billed. Some banks show it on the statement for a short time. Tell your customers this, so that they do not contact support.

Choose a recurring type

Each stored card carries a recurringType. The type is Adyen's term for the agreement the customer gives when they store the card. It tells the card networks who starts later payments, and how often. Plorea passes the value to Adyen and echoes it back. Verified

ValueWho starts later paymentsUse it for
SubscriptionYou or Plorea, on a fixed scheduleEvery card that a Plorea subscription bills. Monthly memberships, yearly licences.
CardOnFileThe customer, each timeOne-click checkout. The customer is present and confirms each payment.
UnscheduledCardOnFileYou, at irregular timesUsage top-ups, no-show fees, auto-reload when a balance runs low.

Use Subscription for every card that the Plorea scheduler will charge. The value is case-sensitive.

Pick the type that matches the agreement

The recurring type is part of the customer's consent. Do not store a card as CardOnFile and then bill it on a schedule. Card networks can treat such charges as unauthorised.

We do not know if Plorea rejects a subscription whose payment method has a different recurring type. Open question

Choose a setup flow

Two endpoints store a card. Both create the same payment method object and both use the 1 NOK verification. They differ in where the card form shows.

Hosted page

POST /payment-methods/setup. Plorea returns an Adyen link. You redirect the customer to it. No front-end code.

Drop-in session

POST /payment-methods/setup/session. You render Adyen Drop-in in your web page or native app.

The company on the card form

On a platform, the card is often saved for one of your clients, not for you. Send that company's merchantOrgNr, and optionally its merchantName. Plorea resolves the company's store from the number. The 3-D Secure challenge then shows the company's name instead of the platform's. On the hosted page, the company's name also shows on the page itself. Both setup flows accept the fields. Stated by Plorea In the PHP SDK, call ->merchant($orgNr, $name) on the setup builder. Without it, nothing extra is sent.

Hosted setup

POST/payment-methods/setup

Use the hosted flow when you do not want card fields in your own front end. Plorea creates an Adyen payment link. You send the customer there.

  1. Create the setupSend the request from your server. Save paymentMethodId immediately, before you redirect. You need it to poll.
  2. Redirect the customerSend the customer to adyenPaymentLinkUrl. Adyen shows the card form and runs 3-D Secure.
  3. Handle the returnAdyen sends the customer to your returnUrl. Do not trust the return as proof. The customer can return without finishing.
  4. Poll for the resultRead the payment method until its status is active or failed. See Poll for the result.
curl -X POST https://payments.plorea.no/payment-methods/setup \
  -H "Authorization: Bearer $PLOREA_API_KEY" \
  -H "X-Environment: test" \

async function plorea(method, path, body) {
  const res = await fetch(`https://payments.plorea.no/${path}`, {
    method,
    headers: {
      Authorization: `Bearer ${process.env.PLOREA_API_KEY}`,
      'X-Environment': 'test',
      'Content-Type': 'application/json',
      Accept: 'application/json',
    },
    body: body ? JSON.stringify({ platform: 'acme', ...body }) : undefined,
  });
  const json = await res.json();
  if (!res.ok) throw Object.assign(new Error(json.error), { status: res.status, body: json });
  return json;
}

Drop-in session setup

Use a session when the card form must live inside your own page or app. Plorea opens an Adyen checkout session for the 1 NOK verification. You mount Adyen Drop-in on the session in the browser or with Adyen's iOS or Android SDK.

Web Drop-in needs a whitelisted origin

In a browser, Adyen accepts the session only from an origin that Plorea has added to the client key. Ask Plorea to add your domains before you go live. Native apps send no origin and are not affected. See Embedded and native checkout for the origin rules and 3-D Secure in native apps.

An abandoned session stays pending

If the customer closes Drop-in without submitting, nothing tells Plorea. The payment method stays pending_setup. Do not wait for it. Start a new setup when the customer tries again. Verified for payment sessions.

Poll for the result

GET/payment-methods/{paymentMethodId}

Plorea sends no webhook for card setup. This applies to success and to failure. You must read the payment method to learn the outcome. Stated by Plorea

Poll from your server, not from the browser. A good pattern:

  1. Poll on returnWhen the customer reaches returnUrl, read the payment method once. Most setups are complete by then.
  2. Poll briefly in the backgroundIf the status is still pending_setup, queue a job. Read again every few seconds for a minute, then less often.
  3. Stop at expiresAtThe setup carries an expiresAt. Stop polling after that time and treat the setup as abandoned.
curl "https://payments.plorea.no/payment-methods/pm_test_golden_method?platform=acme" \
  -H "Authorization: Bearer $PLOREA_API_KEY" \
  -H "X-Environment: test" \
  -H "Accept: application/json"
$method = Plorea::paymentMethods()->find($member->pending_payment_method_id);

if ($method->isActive()) {
    $member->update([
        'payment_method_id' => $method->id,
        'card_label' => "{$method->cardBrand} •••• {$method->cardLast4}",
        'card_expiry' => $method->expiryDate, // "03/2030"
    ]);
} elseif ($method->hasFailed()) {
    // Final. No card was stored. Ask for a new card.
} elseif ($method->isPendingSetup() && $method->expiresAt?->isFuture()) {
    // Not finished yet. Poll again later.
}
// plorea() is the helper from the hosted setup example.
async function waitForCard(id, { until }) {
  for (let delay = 2000; Date.now() < until; delay = Math.min(delay * 2, 30000)) {
    const method = await plorea('GET', `payment-methods/${encodeURIComponent(id)}?platform=acme`);
    if (method.status === 'active' || method.status === 'failed') return method;
    await new Promise((r) => setTimeout(r, delay));
  }
  return null; // abandoned
}

There is no failure reason

A failed setup tells you only that it failed. The response has no refusal reason. A failureReason field, where Plorea returns one, is null even for a real Adyen refusal. Branch on status alone. Show the customer a general message, such as "Your bank declined the card. Try another card." Verified

What would help

A refusalReason on failed setups, and a webhook when a setup becomes active or failed. Both would remove the polling loop. Proposal See Gaps and proposals.

What happens after expiresAt

We have not seen a setup change status when expiresAt passes. We do not know if the Adyen link still accepts a card after that time. Open question Treat a setup that is still pending after expiresAt as abandoned, and create a new one.

Shopper reference

The shopperReference is how Adyen links stored cards to one person. Choose it once per customer and never change it.

  • Make it stable. Use a value from your own database, such as a prefixed member ID. Do not use an email address. Emails change.
  • Make it unique across your tenants. Prefix it with the tenant, for example acme-gym-member-1001.
  • Do not put personal data in it. The value travels to Adyen and appears in reports.

A stored payment method belongs to the shopper, not to a company. One payment method can back subscriptions that bill different companies under the same tenant. Stated by Plorea

Tenant scoping

Every payment method belongs to the tenantId you sent at setup. Use it only with subscriptions in the same tenant. A request that mixes the IDs of two tenants fails with 403 and the message Tenant mismatch. Verified on payment reads.

The PHP SDK sends the tenant from config/plorea.php. Call ->tenant('other-tenant') on the builder to override it for one request.

A subscription needs an active payment method. Create and update both reject any other status with 400. Verified

  "error": "Payment method is not active",

  "status": "failed"

The update response carries error and status only. Read the HTTP status, not the message. Messages are fixed templates. See Errors and retries.

Replace a card

You cannot change the card on an existing payment method. To replace a card, store a new one and point the subscription at it. The price, the schedule and the charge history stay on the subscription.

  1. Store the new cardRun a setup with the same shopperReference. Poll until it is active.
  2. Attach itSend PATCH /subscriptions/{id} with the new paymentMethodId.
  3. Delete the old oneWhen no subscription uses it any more, delete it.
curl -X PATCH https://payments.plorea.no/subscriptions/sub_test_golden \
  -H "Authorization: Bearer $PLOREA_API_KEY" \
  -H "X-Environment: test" \
  -H "Content-Type: application/json" \
  -d '{ "platform": "acme", "paymentMethodId": "pm_new_card" }'
Plorea::subscriptions()
    ->update($subscriptionId)
    ->paymentMethod($newMethod->id)
    ->save();
await plorea('PATCH', `subscriptions/${subscriptionId}`, {
  paymentMethodId: newMethod.paymentMethodId,
});

Delete a card

DELETE/payment-methods/{paymentMethodId}

A delete cancels a stored card so that it can never be charged again. Plorea keeps the record and moves it to cancelled. Captured in test on 2026-10-06. Verified Full shapes: API reference.

curl -X DELETE "https://payments.plorea.no/payment-methods/pm_test_golden_method?platform=acme" \
  -H "Authorization: Bearer $PLOREA_API_KEY" \
  -H "X-Environment: test"
use MemberFlow\Plorea\Exceptions\PaymentMethodInUseException;

try {
    $cancellation = Plorea::paymentMethods()->delete($methodId);

    $cancellation->isCancelled();     // true: status "cancelled"
    $cancellation->previousStatus;    // "active"; null on a repeat call
    $cancellation->alreadyCancelled;  // true on a repeat call
} catch (PaymentMethodInUseException $e) {
    $e->activeSubscriptionIds();      // move these to another card, or cancel them, first
}
// plorea() is the helper from the hosted setup example. It throws on 4xx.
try {
  const cancellation = await plorea('DELETE', `payment-methods/${methodId}?platform=acme`);
  // cancellation.status === 'cancelled'
} catch (err) {
  if (err.status === 400 && err.body.activeSubscriptionIds) {
    // Still in use: move or cancel err.body.activeSubscriptionIds first
  } else {
    throw err;
  }
}
  • Subscriptions block it. A card that a subscription still uses returns 400 with activeSubscriptionIds and activeSubscriptions. A trialing subscription blocks it too. The card stays active.
  • It is idempotent. A repeat delete returns 200 with alreadyCancelled: true, and no previousStatus or cancelledAt.
  • The record stays. A read returns the method as cancelled, with the card fields unchanged. The read has no cancelledAt, so updatedAt is the cancellation time.
  • It cannot be reused. A new subscription on it returns 400 "Payment method is not active".
  • Spelling. Payment methods say cancelled. Subscriptions say canceled.

A sibling method can still be charged

Two payment methods for the same shopper can share one stored card (the same storedPaymentMethodId). A delete cancels only the method you name. In test, the sibling still read active after the delete, and a charge on it was authorised. Verified Production is not observed. To remove a card completely, delete every method that shares its storedPaymentMethodId.

Test cards

Use Adyen's public test cards. 4111 1111 1111 1111, expiry 03/2030, CVC 737 stores successfully. Verified

To test a failed setup, use Adyen's test triggers, such as the holder name NOT_ENOUGH_BALANCE. The trigger refuses the 1 NOK verification. You get a failed payment method. Verified

You cannot store a card that declines later

Every Adyen test card that stores successfully also approves every later charge. So you cannot test a subscription renewal that fails. Not observable in test See Testing and Failed charges and dunning.
