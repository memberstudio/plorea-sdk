Verified behaviour

Dated field notes from running a production integration against the Plorea test environment. Some behaviour is surprising. Some contradicts what you would assume. Knowing what is not verified matters as much as knowing what is.

Verified Seen on the wire. Stated by Plorea Not observed. Not observable in test Open question

Anonymised captures of the real responses back every shape in these docs. If Plorea changes a shape, the capture tests in the PHP SDK fail. Later entries can supersede earlier ones. Superseded entries say so.

Payments

A declined payment reports failed, not refused

Verified 2026-09-09 A card declined after a completed 3-D Secure challenge produced this:

{ "status": "failed", "webhookEventCode": "AUTHORISATION", "webhookSuccess": false }
  • The status string is failed. The string refused never appears.
  • The decline shows in the inbound-webhook fields. They describe the Adyen event that Plorea received.
  • No reason field exists on the payment. status is the only signal.

No idempotency on duplicate references

Verified Two POST /payments/link calls with the same reference create two live, payable links. Check for an existing payment before you create one. See Errors and retries.

Amounts are minor units

Verified 10000 is 100,00 kr. No major-unit form exists anywhere in the API.

Status: 200 for open, 404 for unknown

Verified An open, unpaid link returns 200. Only an unknown reference returns 404.

expired is never reported

Verified A link past its expiry keeps its open status. Use the expiresAt from the create response, or the expired flag on GET /pay/{id}.

Refunds and cancels settle slowly

Verified 2026-09-09 refund_requested and cancel_requested appear at once. In test, a refund stayed in refund_requested for more than 11 hours before payment.refunded arrived. Nothing was wrong.

Set your polling horizon in hours

A job that polls for one hour and then marks the refund as failed will be wrong. Wait for the webhook. Use polling as a backstop, on a scale of hours. Never reverse a refund in your books on a timeout.

Verified 2026-09-09 There is no status per refund. Three captures of a refund-requested payment returned identical 29-key bodies. refundPspReference exists only on the refund response. Store it.

Verified 2026-09-19 A refund and a cancel were both still pending after more than 24 hours. Stated 2026-09-21 Plorea states this is expected, and that the final statuses are refunded and cancelled. Book on the request. Do not wait for the final status.

Capture is automatic

Stated 2026-09-15 Capture runs automatically through Plorea's settlement partner, usually within minutes of authorisation. No capture endpoint exists. A manual capture API is on Plorea's roadmap. For an integrator, authorised is the end of the success path.

merchantOrgNr on payment links

Verified 2026-09-07 The create response omits merchantOrgNr and merchantName. Both appear on GET /pay/{id}, together with a populated partnerSplits.

Stated 2026-08-30 The field is contractually required. The API does not enforce it: a link without it is accepted and can open a session. KYC for a new organisation starts on its first payment.

The platform field

Stated 2026-09-15 Send platform on every request: in the body on POST and PATCH, in the query string on GET. Plorea uses it for logging and reporting only.

A refund without X-Environment hits live

Verified 2026-09-10 POST /payments/refund without the header uses Plorea's live Adyen credentials. With a test key it returns 401 with errorType: "security". The response looks like a bad API key. Send the header on every call.

The refund and cancel 401 is fixed

Verified 2026-09-19 An earlier test-environment configuration issue made refund and cancel return 401. Plorea fixed it on 2026-09-18. A re-test returned refund_requested and cancel_requested normally. In one sample, lastRefundRequestPspReference equalled the refund's refundPspReference.

Client keys and origins

  • Verified The origin allow-list is per client key and applies to browsers only. A request with no Origin header, as a native SDK sends, is accepted.
  • Verified A wildcard origin covers subdomains at any depth. Since 2026-09-19 the bare domain is also whitelisted. localhost is not whitelisted at any port.
  • Verified The hosted pay page uses its own key. That key returns 403 from any other origin. Use the key the session returns.
  • Stated 2026-09-18 Adyen does not check app bundle IDs or package names. Plorea registers them formally before go-live.
  • Stated 2026-09-18 For customers' own domains, route the payment step through your own whitelisted subdomain. No API to register single origins is planned.

Native 3-D Secure arrives as a redirect

Verified 2026-09-17 Plorea's session does not ask for native 3DS2. The challenge opens in an in-app browser and returns through your returnUrl. Handle that redirect on every channel. Stated 2026-09-18 Native 3DS2 for iOS and Android sessions is coming.

An abandoned session never ends

Verified 2026-09-17 A session that the customer never submits still reads created an hour later, with no webhook fields. Time the attempt out yourself. Open a new session for the next attempt.

Payment methods

Statuses

Verified 2026-09-04 pending_setup → active or failed. failed is final. It means the 1 NOK verification was refused, so no card was stored and storedPaymentMethodId stays null.

failureReason is always null

Verified 2026-09-09 Also for a real refusal. Branch on status only.

Validation messages are static

Verified 2026-09-09 A request that misses two required fields returns a message that lists all five. Never parse a validation message.

No webhook for setup

Stated 2026-09-09 Poll GET /payment-methods/{id} after the customer returns.

Subscriptions

Statuses use US spelling

Verified 2026-09-07 active, trialing, canceled. trialing is its own state. payment_failed is documented but has never been observed.

Billing starts immediately

Verified Without a trial, the scheduler charges within seconds of create.

Trials

Verified 2026-09-07 With trialEndsAt set, the status is trialing and nextChargeAt equals trialEndsAt. Nothing is charged until then. A cancel during a trial returns accessEndsAt: null. Treat null as "access ends now".

merchantOrgNr on subscriptions

Verified 2026-09-21 POST /subscriptions accepts merchantOrgNr, merchantName and merchantEmail. The create response echoes only merchantOrgNr. A value that is not nine digits returns 400. No read endpoint returns the field. Keep your own record.

Stated 2026-09-21 Every charge inherits the company. KYC and settlement splits start on the first charge. A stored card belongs to the shopper, not the company, so one card can pay for several companies in one tenant. No API exists to start or read KYC. To onboard a company early, create a payment link with its organisation number and pay it yourself.

Charge shapes

Verified 2026-09-04 POST …/charge returns status: "charge_created" and Adyen's resultCode. History items show status: "authorised" and reason manual_charge or scheduled_charge. The reference is {subscriptionId}-{chargeId}.

Not chargeable is 400, not 402

Verified 2026-09-04 A subscription that cannot be charged, and a payment method that is not active, both return 400. 402 means a card decline only.

Reactivate no longer double-bills

Verified 2026-09-09 Reactivate used to charge at once, billing a period the customer had already paid. Plorea fixed it. Now a cancel and reactivate leaves the charge count unchanged and sets nextChargeAt to one interval after the last charge. Reactivating an active subscription returns 400 "Only canceled subscriptions can be reactivated". Production is unobserved.

Scheduled charge references do not resolve as payments

Open question GET /payments/status/{subId}-{chgId} for a scheduled charge returned 403 Tenant mismatch on 2026-09-04 and 404 on 2026-09-09. Manual charge references resolve normally. Read scheduled outcomes from GET /subscriptions/{id}/charges. Reported to Plorea.

No pagination seen

Open question Probed 2026-09-10. GET /subscriptions returns {count, items} plus the filter echo. GET …/charges returns {subscriptionId, items}. Neither has a cursor or page field. With only three items available, "all results" and "first page" look the same.

Webhooks

Deliveries are signed

Verified 2026-08-26 No Authorization header. Three headers instead: x-plorea-signature (base64 HMAC-SHA256 of the raw body), x-plorea-event-id and x-plorea-event. The signature covers the body only, so the headers can change without breaking it. Deduplicate on the body's eventId.

Signature verification proven

Verified 2026-09-09 The key is the secret's characters used verbatim, not decoded bytes. A genuine replayed delivery was accepted. The same delivery with a one-byte change was rejected. Any middleware that re-encodes the body before verification breaks it.

Subscription deliveries

Verified 2026-09-04 A scheduled charge sends subscription.charge_succeeded. A manual charge sends payment.authorised with the normal payment shape.

payment.failed

Verified 2026-09-09 Arrived about two seconds after the status changed. The type is payment.failed in the header and the body. The body has eventCode: "AUTHORISATION" and success: false, and no reason. data is a strict subset of the payment object.

Routing and redelivery

  • Stated 2026-09-21 Registration is manual and per tenant. Plorea can register one URL per environment on request. Before that, one URL received both.
  • Stated 2026-09-21 The same signing secret can serve both environments. Ask; do not assume.
  • Stated 2026-09-21 A failed delivery is not retried. A 500 from your endpoint loses the event.
  • Stated 2026-09-09 Four event types exist. Nothing is sent for card setup, cancel, reactivate or a failed charge.

What test cannot reproduce

A failed subscription charge

Impossible in test, 2026-09-09 These shapes cannot be produced: the 402 body of a declined charge, a payment_failed subscription, a filled failureReason, a non-zero retryCount, and any failed-charge webhook.

  1. Adyen triggers declines through fields on the payment request, such as the holder name. For a stored card, that request is the setup. A decline trigger therefore fails the setup, and no card is stored.
  2. Custom test cards carry no decline behaviour.
  3. Every published Adyen test card approves and has a future expiry.
  4. Amount-based triggers apply to terminals only.
  5. Plorea's scheduler charges the stored card server-side, with no way to pass a trigger.

Unblocking this needs Plorea. See Sandbox failure triggers.

A declined one-off payment

Reproducible Pay a hosted link with card 4000 0000 0000 0259. Adyen does not recognise it and declines after the 3-D Secure challenge.
