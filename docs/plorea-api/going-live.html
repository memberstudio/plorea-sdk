Integration

Going live

A checklist for moving from test to production. Each item has either failed silently or cost real money when someone missed it. Work through it in order, then run one real transaction end to end.

1. Credentials and environment

  1. Get a live API key from PloreaDo not reuse the test key. Store the live key only in the production environment, in a secret store.
  2. Send X-Environment: live on every requestMost endpoints default to test when the header is missing. An unset variable therefore sends production traffic to test. Verified
  3. Set your production tenant IDIf Plorea gave you a different tenant for live.
  4. Set your platform valuePlorea uses it to attribute your traffic. It has no functional effect. Stated by Plorea
  5. Rotate any exposed keyAnyone with the key can create links and refund payments. If the key has been in a chat, a ticket or a log, ask Plorea for a new key before launch.
PLOREA_API_KEY=...                  # live key from Plorea
PLOREA_ENVIRONMENT=live             # sent as X-Environment
PLOREA_TENANT_ID=acme
PLOREA_PLATFORM=acme
PLOREA_RETRY_TIMES=0                # keep 0 — see Errors and retries
PLOREA_WEBHOOK_SECRET=...           # live signing secret
PLOREA_ADYEN_CLIENT_KEY=live_...    # only for embedded checkout

Check the environment in a response

After deploy, create one link and confirm that the response reads "environment": "live". We have not observed a live value ourselves. Open question

2. Merchants, KYC and payouts

The merchantOrgNr decides who receives the money. Set it to the organisation number of the company that issues the invoice, not your own.

  • Send merchantOrgNr on every payment link and subscription. Plorea requires it by contract. Stated by Plorea The API does not enforce it on payment links: a link without it is accepted. Verified Enforce it in your own code.
  • Use nine digits. On POST /subscriptions, any other value returns 400 "Invalid merchantOrgNr — must be 9 digits". Verified
  • Tell each merchant about KYC. The first live payment for a new organisation number starts onboarding by email. The payment succeeds. The payout waits until KYC is approved, which takes 1 to 5 business days. Stated by Plorea
  • Onboard a merchant ahead of time if needed. No API exists to start or read KYC. Plorea suggests a small payment link with the merchant's organisation number, paid by yourself. Stated by Plorea
  • Keep your own record of which company each subscription bills for. Reads of a subscription do not return merchantOrgNr. Verified

Missing: KYC status

An endpoint that reports the KYC and payout status of an organisation number would let you warn a merchant before money is held. Proposal

3. Webhooks

  • Register your production URL with Plorea, for example https://api.example.com/plorea/webhook. Registration is manual. Ask for a separate URL per environment. Stated by Plorea
  • Get the live signing secret through a secure channel. Ask Plorea if it differs from the test secret. Both environments can share one.
  • Verify every signature. Never disable verification in production.
  • Exclude the path from CSRF protection. Otherwise every delivery fails with 419 and nothing reaches your listeners.
  • Store first, then process in a queue. Plorea does not redeliver a failed delivery. Stated by Plorea
  • Deduplicate on eventId from the body.

See Webhooks.

4. Embedded and native checkout

Skip this section if you use hosted payment links only.

  • Use a live Adyen client key. A test key does not work with live sessions. The PHP SDK throws if the key prefix (live_) does not match the environment.
  • Get your production origins whitelisted for the live key. The origin allow-list is per key and applies only to browsers. A wildcard covers subdomains at any depth but not always the bare domain. localhost was not whitelisted on the key we tested; ask Plorea if you need it. Verified
  • Route customer-owned domains through your own subdomain. No API exists to register single origins. Stated by Plorea
  • Register your production app identifiers with Plorea for native apps.
  • Test return URLs in production builds. Universal links and App Links must verify on the production domain. A custom-scheme return URL is accepted. Verified
  • Allow Adyen's live hosts in your Content Security Policy. They differ from the test hosts.
  • Configure wallets if you show them, for example Apple Pay domain verification on each domain.

See Embedded and native checkout.

5. Money-handling code

  • Keep automatic retries off for writes. A retried link create or charge can bill twice. See Retries and idempotency.
  • Create links with a check-first pattern inside a lock per reference (firstOrCreate() in the PHP SDK).
  • Book payments idempotently on the reference. The webhook, a status poll and the customer's return page race.
  • Compare the amount on the payment with the amount you expect before you book it.
  • Treat authorised as paid. Capture is automatic. No capture API exists. Stated by Plorea
  • Store the refund response. refundPspReference exists only there. You cannot read it back later. Verified
  • Size refund polling in hours. Never tell a customer that a refund failed, or reverse it in your books, because of a timeout alone.
  • Cancel before settlement, refund after. See Refunds and cancellations.

6. Monitoring

Alert onWhy
Any response with status 400 or higherA 400 on a charge is a bug in your state handling. A 401 can mean a wrong environment.
Connection errors and timeoutsThe outcome of a write is unknown until you read state back.
Webhook signature failuresA wrong secret, a body-rewriting proxy, or an attack.
Links open past expiresAtThe status never reports expired.
Card setups in pending_setup past expiresAtNo webhook is sent for setup.
Subscriptions with nextChargeAt in the pastA failed scheduler charge sends no webhook. See Failed charges and dunning.
Refunds in refund_requested for more than a few daysSettlement is slow, but not that slow.

Never log request headers. The API key is in Authorization.

7. Reconciliation

Webhooks can be missed, and several transitions send none. Run a scheduled job that reads state directly from the API.

# All subscriptions for one of your entities. Do not filter on status:
# status=active hides payment_failed and overdue trials.
curl "https://payments.plorea.no/subscriptions?externalId=membership-42&platform=acme" \
  -H "Authorization: Bearer $PLOREA_API_KEY" \
  -H "X-Environment: live"
// Schedule hourly.
foreach ($openInvoices as $invoice) {
    $status = Plorea::payments()->status($invoice->reference);
    if ($status->isPaid()) {
        $invoice->markPaid($status->pspReference); // idempotent
    }
}

foreach ($workspaces as $workspace) {
    Plorea::subscriptions()
        ->needingAttention($workspace->externalId)
        ->each(fn ($subscription) => Dunning::start($subscription));
}
// Schedule hourly.
const res = await fetch(
  // No status filter: status=active hides payment_failed and overdue trials.
  'https://payments.plorea.no/subscriptions?externalId=membership-42&platform=acme',
  { headers: { Authorization: `Bearer ${process.env.PLOREA_API_KEY}`, 'X-Environment': 'live' } },
);
const { items } = await res.json();
const flagged = items.filter((s) =>
  s.status === 'payment_failed' ||
  (s.status !== 'canceled' &&
    s.nextChargeAt &&
    new Date(s.nextChargeAt).getTime() < Date.now() - 60 * 60 * 1000),
);
for (const s of flagged) await startDunning(s);

Also reconcile money against Adyen payouts in your accounting. The API has no payout or settlement report endpoint. Open question

8. The launch test

Use a merchant with completed KYC

Otherwise the payout waits and you cannot confirm the full money path.

  1. Create a low-value live linkFor example 10,00 kr.
  2. Pay it with a real cardDo it on every surface you ship: hosted page, web Drop-in, iOS and Android.
  3. Check the webhookConfirm that it arrived, passed verification and was booked once.
  4. Refund the paymentConfirm refund_requested. Check again after some hours.
  5. Test a subscriptionIf you sell subscriptions, store a card and let the scheduler charge it.
  6. Check the payoutConfirm the money reaches the merchant's account.
