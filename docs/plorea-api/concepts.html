Core concepts

The ideas that every Plorea endpoint shares. Learn them once and the rest of the API becomes predictable: who owns which identifier, how test and live are kept apart, how money is written, and which calls are safe to retry.

References

The reference is the key of a one-off payment. You choose it when you create the link. You use it to read the status, refund, cancel and match webhooks. Plorea passes it to Adyen as the merchant reference.

  • Make it unique per payment attempt. Use your order or invoice number. If you need a second attempt for the same order, add a suffix, for example ORDER-1001-1.
  • Keep it stable. Store it on your order before you call Plorea. Then a crash after the call still leaves you a key to look up.
  • A modification has its own reference. A refund or cancel takes a modificationReference. Make it unique per attempt, for example ORDER-1001-refund-1.

Subscription charges get a reference from Plorea in the form {subscriptionId}-{chargeId}. Verified A manual charge resolves on GET /payments/status/{reference}. A scheduled charge does not: the call answers 404. Read scheduled charges from GET /subscriptions/{id}/charges. Open question

Tenants and customers

Plorea is built for platforms that serve many businesses. Two levels of identifiers keep their data apart.

tenantId
One of your own clients, for example one club or one shop. Plorea issues tenant IDs. Every write takes it in the body. Stored cards, subscriptions and payments belong to one tenant. A request that reads an object of another tenant fails with 403 and "Tenant mismatch". Verified
customerId
Your identifier for the paying person inside the tenant. Optional, but send it. It lets you find stored cards and subscriptions per person.
shopperReference
The identifier Adyen stores the card under. A stored card is tied to the shopper reference, not to a company. One card can pay subscriptions for different organisation numbers in the same tenant. Stated by Plorea
externalId
Your identifier for a subscription, for example your own membership ID. List subscriptions by it with GET /subscriptions?externalId=….

The merchant: who gets the money

The tenant groups your data. The merchant is the company that receives the payout. You name it with merchantOrgNr, the Norwegian organisation number of the invoice issuer. Never send your own platform's number unless you are the seller.

  • Plorea requires it by contract on payment links. Stated by Plorea The payment-link endpoint does not enforce it. Verified
  • On a subscription the field is optional. Every charge inherits the company. A subscription without it behaves as before. Stated by Plorea
  • On subscriptions the value must be nine digits. Otherwise the API answers 400. Verified
  • The first payment for a new organisation number starts KYC automatically. The payout waits until KYC is approved, usually 1–5 business days. The link stays payable. Stated by Plorea
  • Reads do not return the merchant on subscriptions, and the link-create response does not echo it. Keep your own record. Verified

Environments

Test and live share one host, https://payments.plorea.no. The X-Environment header selects the Adyen account behind the call.

environment in responsestest Verifiedlive Not observed
Webhook URLOne URL per environment, on request. Not the default. Stated by Plorea

A missing header can reach live

Most endpoints default to test when the header is missing. POST /payments/refund does not: it routes to the live credentials and answers 401 with "errorType": "security". The error looks like a bad key. Send X-Environment on every request, from one place in your code. Verified

Payment, payment-method and session responses and webhooks carry environment. Subscription responses and error bodies do not. Keep the environment of each request in your own context. Check it in your webhook handler. Drop events whose environment does not match the server that receives them.

Amounts and currency

All amounts are integers in minor units. For NOK, that is øre. There is no decimal form anywhere in the API. Verified

The shape differs by endpoint. Payment links and refunds use a flat integer plus a separate currency. Subscriptions and charges use an object.

// POST /payments/link — flat
{ "amount": 24900, "currency": "NOK" }

// POST /subscriptions — object
{ "amount": { "value": 24900, "currency": "NOK" }, "vatRate": 0.25, "vatAmount": 4980 }
use MemberFlow\Plorea\Data\Amount;

$price = Amount::nok(24900);
$price->value;          // 24900
$price->inMajorUnits(); // 249.0
$price->toArray();      // ['value' => 24900, 'currency' => 'NOK']
// Keep money as integers. Convert only for display.
const toOre = (kroner) => Math.round(kroner * 100);
const format = (ore) =>
  new Intl.NumberFormat('nb-NO', { style: 'currency', currency: 'NOK' }).format(ore / 100);

VAT on subscriptions is a decimal rate (0.25 for 25 %) plus the VAT amount in øre. You calculate the VAT amount yourself. Plorea does not check that the two agree.

The platform field

Plorea asks each integrator to name itself with platform. Plorea uses the value for logging and reporting. It has no effect on any endpoint. Stated by Plorea

  • On POST and PATCH: send it in the JSON body.
  • On GET: send it in the query string, for example ?platform=acme.

A payment that a manual subscription charge created reports "platform": "subscription" on the status endpoint. Verified

Idempotency and retries

Plorea has no idempotency keys. The API does not detect a duplicate request. This is the most important fact for your retry logic. Verified

CallSafe to retry?Why
Any GETYesReads change nothing.
POST /payments/refund, /payments/cancelWith the same modificationReferenceThe modification reference identifies the attempt. Open question: Plorea has not confirmed that it rejects a repeat.
POST /payments/linkNoA repeat creates a second payable link with the same reference. Verified
POST /subscriptionsNoA repeat creates a second subscription that bills the card again.
POST /subscriptions/{id}/chargeNoA repeat charges the card again.

Use a "look up, then create" pattern for unsafe calls:

  1. Look up firstFor a link, call GET /payments/status/{reference}. For a subscription, call GET /subscriptions?externalId=….
  2. Reuse an open matchIf a link is open with the same amount and not expired, send the customer to it.
  3. Stop on a paid matchIf the reference is already paid, never create another link for the same order.
  4. Supersede a dead matchIf the link is expired, cancelled or has a different amount, create a new link on a suffixed reference (-1, -2, …).
  5. Lock per referenceTwo requests can race between the lookup and the create. Hold a lock on the reference across both steps.

The PHP SDK implements this pattern as firstOrCreate(). See Payment links.

What would fix this

An Idempotency-Key header on every POST, or a 409 on a duplicate reference. Proposal See Gaps and proposals.

Timestamps

Timestamps are ISO 8601 strings. Plorea returns UTC with milliseconds, for example 2026-09-04T09:55:00.000Z. Some fields on stored cards carry a local offset, for example 2026-09-05T11:51:00+02:00. Parse both forms. Send dates with an explicit offset.

Webhooks are signals, not facts

A webhook tells you that something changed. It does not replace a read. Delivery can fail, and Plorea does not redeliver. Stated by Plorea Some changes send no webhook at all: card setup, cancel, reactivate and a failed subscription charge. Stated by Plorea

So every integration needs two paths to the same code: a webhook handler and a scheduled poll. Both re-read the object and apply the result idempotently. See Webhooks.

The evidence model

Plorea has not published an API contract. These docs therefore say where each claim comes from.

BadgeMeaningHow much to trust it
VerifiedWe called the test API and saw it. Anonymised captures back most of these.High for test. Production can differ.
Stated by PloreaPlorea told us in writing. We could not observe it.Build on it, but add a guard.
Not observable in testThe test environment cannot produce it, for example a failed scheduled charge.Handle it defensively.
Open questionUnknown. We have asked Plorea.Do not depend on any answer.
ProposalA change we ask Plorea to make.Not available today.

Two rules follow from this model:

  • Branch on status strings and HTTP codes only. Error messages are fixed templates and can change. Never parse them. Verified
  • Tolerate unknown fields and values. Plorea adds fields without notice. Keep the raw response, and treat an unknown status as "needs review", not as success.
