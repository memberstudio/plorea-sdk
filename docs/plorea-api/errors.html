Errors and retries

How the Plorea API reports errors, what each HTTP status means, and which requests you can safely send again. Money-moving calls have no idempotency key, so retry logic needs care.

The error body

An error response has a JSON body with an error string. Some errors add context fields, such as the current status or the ID that caused the error. Verified

{
  "error": "Subscription is not chargeable",
  "subscriptionId": "sub_test_example",
  "status": "canceled"
}
{
  "error": "Payment not found",
  "reference": "order-9999"
}
{ "error": "Tenant mismatch" }

The body shape is not fully consistent across endpoints. Read error first, then message, then fall back to the raw body. The SDK does this for you. Verified

400 versus 402

This distinction matters for subscriptions. 400 means your app sent a charge it should not have sent: the subscription is cancelled, or its card is not active. 402 means the card was declined. Verified for 400. Not observable in test for 402: a declined recurring charge cannot be produced with Adyen test cards, so the 402 body shape is unknown.

The 401 that is not about the key

Check X-Environment before you rotate your key

A POST /payments/refund without X-Environment goes to the live Adyen credentials. With a test key it answers 401 with "errorType": "security". Nothing in the body mentions the environment, so it looks like a bad key. Verified

This trap appears mostly in hand-written curl calls. The SDK sends the header on every request.

Validation messages are static

Plorea returns a fixed template, not a list of the fields that actually failed. A request with two missing fields gets a message that names all five required fields. Verified

{ "error": "tenantId, paymentMethodId, recurringType, amount and interval are required" }
  • Log the message and show it to developers.
  • Never parse it.
  • Never show it to a customer as a list of fields to fix.
  • Validate your own input before you call the API.

Handling errors in code

The PHP SDK maps each status to an exception. Every exception extends MemberFlow\Plorea\Exceptions\PloreaException, so one catch covers the package.

ServerException5xx
RequestExceptionParent of the five above, and any other non-2xx status. Exposes $status and $response.
ConnectionExceptionThe API could not be reached, or the request timed out. The API key is redacted from the wrapped exception chain.

# {"error":"Subscription is not chargeable","subscriptionId":"sub_test_example","status":"canceled"}
# HTTP 400
use MemberFlow\Plorea\Exceptions\ChargeFailedException;
use MemberFlow\Plorea\Exceptions\ConnectionException;
use MemberFlow\Plorea\Exceptions\ValidationException;
use MemberFlow\Plorea\Facades\Plorea;

try {
    $charge = Plorea::subscriptions()->charge($subscriptionId);
} catch (ChargeFailedException $e) {
    // 402: the card was declined. Start dunning.
    $e->status;             // 402
    $e->response?->json();  // raw error body
} catch (ValidationException $e) {
    // 400: not chargeable (cancelled, or card not active).
    // A bug in your own state handling. Do not retry.
    report($e);
} catch (ConnectionException $e) {
    // Unknown outcome. Re-read the charge history before you act.
    $charges = Plorea::subscriptions()->charges($subscriptionId);
}
class PloreaError extends Error {
  constructor(status, body) {
    super(body?.error ?? body?.message ?? `HTTP ${status}`);
    this.status = status;
    this.body = body;
  }
}

async function plorea(path, { method = 'GET', body } = {}) {
  const res = await fetch(`https://payments.plorea.no${path}`, {
    method,
    headers: {
      Authorization: `Bearer ${process.env.PLOREA_API_KEY}`,
      'X-Environment': process.env.PLOREA_ENVIRONMENT ?? 'test',
      'Content-Type': 'application/json',
      Accept: 'application/json',
    },
    body: body ? JSON.stringify({ platform: 'acme', ...body }) : undefined,
    signal: AbortSignal.timeout(30_000),
  });
  const text = await res.text();
  const json = text ? JSON.parse(text) : null;
  if (!res.ok) throw new PloreaError(res.status, json);
  return json;
}

try {
  await plorea(`/subscriptions/${id}/charge`, { method: 'POST', body: {} });
} catch (e) {
  if (e.status === 402) startDunning(id);
  else if (e.status === 400) reportBug(e);
  else throw e;
}

Not found is normal

Use 404 to answer "does this payment exist?". An open link that nobody has paid returns 200. Only a reference that Plorea has never seen returns 404. Verified

try {
    $status = Plorea::payments()->status($reference);
} catch (NotFoundException) {
    $status = null; // never created
}

Retries and idempotency

The Plorea API has no idempotency keys. Two identical POST /payments/link calls create two payable links. Two identical charge calls bill the card twice. Verified for payment links.

OperationSafe to retry?Why
All GET requestsYesReads change nothing.
POST /payments/refundUnknown Open questionPlorea has not confirmed that a repeated modificationReference is deduplicated. Read the payment status before any retry. Do not retry automatically.
POST /payments/cancelUnknown Open questionSame as refund. Check lastCancelReference.
POST /payments/linkNoA retry can create a second live link for the same reference.
POST /subscriptions/{id}/chargeNoNo idempotency key. A retry can charge twice.
POST /subscriptionsNoA retry can create two subscriptions. Billing starts immediately on each.
POST /payment-methods/setup, …/setup/sessionMostly harmlessCreates an extra pending_setup method that nobody completes.
PATCH /subscriptions/{id}YesSets absolute values.
POST /subscriptions/{id}/cancel, …/reactivateYes, but expect 400The second reactivate answers "Only canceled subscriptions can be reactivated".

A timeout is an unknown, not a failure

When a write times out, you do not know if Plorea processed it. Read the state back before you decide.

  1. Payment link timed outCall GET /payments/status/{reference}. A 200 means the link exists. Reuse it. A 404 means you can create it.
  2. Charge timed outCall GET /subscriptions/{id}/charges. Look for a new manual_charge item before you charge again.
  3. Subscription create timed outCall GET /subscriptions?externalId=…. Look for a subscription with your externalId.
  4. Refund or cancel timed outCall GET /payments/status/{reference}. If lastRefundReference or lastCancelReference equals your modificationReference, Plorea accepted it. Otherwise, escalate to a person. Do not retry automatically: Plorea has not confirmed that a repeated modificationReference is safe. Open question

Create payment links safely

The SDK provides firstOrCreate(). It reads the status of the reference first. If an open, reusable link exists, it returns that link. If the reference is already paid, it throws PaymentAlreadyPaidException. If a link exists but cannot be reused, for example because it expired, it creates a new link on a suffixed reference: order-1001-1, order-1001-2, and so on. Run it inside a lock per reference. Without the SDK, use the walk in Duplicate references and firstOrCreate.

# 1. Check first.
curl -s -o /dev/null -w '%{http_code}' \
  "https://payments.plorea.no/payments/status/order-1001?platform=acme" \
  -H "Authorization: Bearer $PLOREA_API_KEY" -H "X-Environment: test"
# 404 -> safe to create. 200 -> inspect status and expiresAt before creating.
use Illuminate\Support\Facades\Cache;
use MemberFlow\Plorea\Data\Amount;
use MemberFlow\Plorea\Exceptions\PaymentAlreadyPaidException;

// The lock must outlive the whole walk: each request can take 30 s,
// and firstOrCreate() sends several. block() releases it when done.
$link = Cache::lock("plorea:link:{$invoice->reference}", 900)->block(10, function () use ($invoice) {
    try {
        return Plorea::payments()
            ->link($invoice->reference, 'Invoice '.$invoice->number, Amount::nok($invoice->total), 'https://example.com/return')
            ->merchant(orgNr: '999999999')
            ->firstOrCreate();
    } catch (PaymentAlreadyPaidException $e) {
        $invoice->markPaid($e->status->pspReference);
        return null;
    }
});
// Plorea has no firstOrCreate. Build it yourself: read the base
// reference, then each suffix (order-1001-1, order-1001-2, ...).
// Keep the first reusable link you find. Create a new link only on the
// first suffix that returns 404. Hold the lock for the whole walk.

Automatic retries in the SDK

PLOREA_RETRY_TIMES retries connection errors and 5xx responses. The default is 0 on purpose. A retry of a non-idempotent write can bill twice. Turn it on only if every write you send is safe to retry.

PLOREA_CONNECT_TIMEOUT10 sTime to open the connection.
PLOREA_RETRY_TIMES0Retries on connection errors and 5xx.

Plorea does not publish timeouts or rate limits. Open question

Never log the API key

The API key can create links and refund payments. Keep it out of logs and error reports.

  • Do not log request headers.
  • The PHP SDK strips the Authorization header from exceptions on both the response path and the connection path.
  • If the key appears in a chat, a ticket or a log, ask Plorea for a new key.

What would help

  • An Idempotency-Key header on link create, subscription create and charge. Proposal
  • Stable machine-readable error codes next to the human message, for example "code": "payment_method_not_active". Proposal
