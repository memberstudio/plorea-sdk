Quickstart

Take a test payment end to end in about ten minutes. You create a payment link, pay it with an Adyen test card, read the result and receive the webhook. The last section stores a card and starts a subscription on it.

Before you begin

You need three things from Plorea. Plorea issues all three by hand. There is no self-service dashboard.

ItemExampleWhat it is for
Test API keyplr_test_FAKE0000000000000000The bearer token on every request. Test keys start with plr_test_.
Tenant IDacme-testThe tenantId you send in request bodies. Plorea scopes data by tenant.
Webhook signing secretwhsec_FAKE…The key to verify webhook signatures. Only needed for step 5.

You also need an organisation number for the company that receives the money. In test, use the reserved value 999999999.

Keep the key secret

Use the API key only on your server. Never put it in a browser, a mobile app or a log line. Store it in an environment variable.

export PLOREA_API_KEY="plr_test_FAKE0000000000000000"
export PLOREA_TENANT_ID="acme-test"

The flow you will build

Step 1: Create a payment link

A payment link is a hosted page on pay.plorea.no. You choose the reference. It identifies the payment in every later call. Use your own order or invoice number.

POST/payments/link
curl https://payments.plorea.no/payments/link \
  -H "Authorization: Bearer $PLOREA_API_KEY" \
  -H "X-Environment: test" \
  -H "Content-Type: application/json" \
  -d '{
    "platform": "acme",
    "tenantId": "acme-test",
    "reference": "ORDER-1001",
    "product": "Annual membership",
    "amount": 10000,
    "currency": "NOK",
    "email": "buyer@example.com",
    "returnUrl": "https://shop.example.com/orders/1001/return",
    "merchantOrgNr": "999999999",
    "merchantName": "Acme AS",
    "merchantEmail": "billing@example.com"
  }'
use MemberFlow\Plorea\Data\Amount;
use MemberFlow\Plorea\Facades\Plorea;

$link = Plorea::payments()
    ->link(
        reference: 'ORDER-1001',
        product: 'Annual membership',
        amount: Amount::nok(10000),          // 100,00 kr
        returnUrl: 'https://shop.example.com/orders/1001/return',
    )
    ->payerEmail('buyer@example.com')
    ->merchant(orgNr: '999999999', name: 'Acme AS', email: 'billing@example.com')
    ->create();

$link->url;        // send the customer here
$link->id;         // pl_...
$link->expiresAt;  // store this

Do not retry a create blindly

The API does not deduplicate references. If a create times out and you send it again, the customer can get two payable links for one order. Read the status of the reference first. A 404 means no link exists yet. Verified

Why send merchantOrgNr in test

The organisation number tells Plorea which company gets the payout. The API accepts a link without it, but Plorea requires it by contract. Send it from day one so your code is ready for live. Stated by Plorea The create response does not echo it back. Verified

Step 2: Open the link

Redirect the customer to paymentLinkUrl. For this test, open it in your own browser. The page shows the product, the amount and an Adyen card form.

Step 3: Pay with a test card

Use an Adyen test card. The test environment never moves real money.

Adyen publishes the full list of test cards in its own documentation. After payment, the page sends the customer to your returnUrl.

The return URL proves nothing

Anyone can open your return URL. The customer can also close the tab before the redirect. Never mark an order as paid because the customer came back. Read the status in step 4.

Step 5: Receive the webhook

Plorea posts a signed event to your webhook URL when the payment is authorised or fails. Plorea registers the URL by hand, per tenant. Plorea can register one URL for test and one for live, on request. Stated by Plorea

  1. Expose a local URLRun a tunnel tool, for example cloudflared or ngrok, in front of your local server. You get a public HTTPS address.
  2. Register the URLSend the URL to Plorea through a secure channel. Ask for it as your test URL. Get the signing secret back.
  3. Verify the signatureCompute the base64 HMAC-SHA256 of the raw body with the secret as the key. Compare it with x-plorea-signature in constant time.
  4. Read the status againUse the reference in the event to call GET /payments/status/{reference}. Book on that answer.
  5. Answer 200 quicklyPlorea does not retry a failed delivery. Do the heavy work in a queue. Stated by Plorea

# Check a signature by hand. body.json holds the raw body, byte for byte.
openssl dgst -sha256 -hmac "$PLOREA_WEBHOOK_SECRET" -binary body.json | base64
// The SDK registers POST /plorea/webhook and verifies the signature
// with PLOREA_WEBHOOK_SECRET. Listen for the event it dispatches.
use Illuminate\Support\Facades\Event;
use MemberFlow\Plorea\Events\PaymentStatusUpdated;
use MemberFlow\Plorea\Facades\Plorea;

Event::listen(PaymentStatusUpdated::class, function (PaymentStatusUpdated $event) {
    // Deduplicate on $event->eventId, then re-fetch the truth.
    $status = Plorea::payments()->status($event->reference);

    if ($status->isPaid()) {
        Order::where('reference', $event->reference)->first()?->markPaid();
    }
});
import crypto from 'node:crypto';
import express from 'express';

const app = express();

// Keep the raw bytes. A JSON parser that re-encodes the body breaks the HMAC.
app.post('/plorea/webhook', express.raw({ type: 'application/json' }), async (req, res) => {
  const expected = crypto
    .createHmac('sha256', process.env.PLOREA_WEBHOOK_SECRET) // the secret string, verbatim
    .update(req.body)
    .digest('base64');
  const given = req.get('x-plorea-signature') ?? '';

  const ok = given.length === expected.length &&
    crypto.timingSafeEqual(Buffer.from(given), Buffer.from(expected));
  if (!ok) return res.sendStatus(403);

  const event = JSON.parse(req.body.toString('utf8'));
  await queue.add('plorea-event', event); // dedupe on event.eventId in the worker
  res.sendStatus(200);
});

No webhook yet? Poll

Registration takes a round trip with Plorea. Until then, poll GET /payments/status/{reference} after the customer returns, and on a schedule for open orders. Keep the poll as a backstop after webhooks work too, because a lost delivery is never sent again.

Next: store a card and start a subscription

Recurring billing has two parts. First the customer stores a card. Then you create a subscription on that card. Plorea runs the scheduler and charges the card on each interval.

Store a card

Create a setup. Plorea returns a hosted Adyen page. The customer enters the card there. Adyen makes a 1 NOK verification authorisation. Verified

Create a subscription

Create the subscription on the active card. Billing starts at once: without a trial, the scheduler charges the first period within seconds. Verified

POST/subscriptions
curl https://payments.plorea.no/subscriptions \
  -H "Authorization: Bearer $PLOREA_API_KEY" \
  -H "X-Environment: test" \
  -H "Content-Type: application/json" \
  -d '{
    "platform": "acme",
    "tenantId": "acme-test",
    "customerId": "cust_42",
    "paymentMethodId": "pm_test_example",
    "recurringType": "Subscription",
    "amount": { "value": 24900, "currency": "NOK" },
    "interval": { "unit": "month", "count": 1 },
    "externalId": "acme-membership-42",
    "title": "Acme membership",
    "vatRate": 0.25,
    "vatAmount": 4980,
    "merchantOrgNr": "999999999"
  }'
use MemberFlow\Plorea\Data\Amount;
use MemberFlow\Plorea\Data\BillingInterval;

$subscription = Plorea::subscriptions()
    ->create('pm_test_example', Amount::nok(24900), BillingInterval::monthly())
    ->customerId('cust_42')
    ->externalId('acme-membership-42')
    ->title('Acme membership')
    ->vat(rate: 0.25, amount: 4980)
    ->merchant(orgNr: '999999999')
    ->save();

$subscription->nextChargeAt; // the first charge, which is now

Each scheduled charge sends a subscription.charge_succeeded webhook. A failed charge sends nothing, so you must poll for it. Read Subscriptions and Failed charges and dunning before you go live.
