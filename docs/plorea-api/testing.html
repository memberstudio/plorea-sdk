Testing

Plorea's test environment runs against Adyen's test platform. You can pay links, store cards, run subscriptions and receive real signed webhooks without moving money. This page explains how, and lists what the test environment cannot show you.

Test and live share one host

Only the X-Environment header separates them. Most endpoints default to test when the header is missing, but POST /payments/refund goes to live and fails with 401. Always send the header. Verified

Test cards

Use the cards on Adyen's published test card list. Each card has a fixed future expiry date and a fixed CVC. Most cards on the list approve. Verified A few always fail, such as the card under "Declined one-off payment" below.

Run every flow once

  1. Payment linkCreate a link for 10,00 kr (1000). Pay it. Check that GET /payments/status/{reference} reads authorised and that a payment.authorised webhook arrives.
  2. Declined paymentCreate a second link and pay it with the decline card. Check for failed and payment.failed.
  3. RefundRefund the first payment. Expect refund_requested at once. Expect the final state many hours later.
  4. CancelPay a third link and cancel it. Expect cancel_requested.
  5. Store a cardRun a card setup. Poll GET /payment-methods/{id} until it reads active.
  6. SubscriptionCreate a subscription with interval: {unit: "day", count: 1}. The first charge runs at once. The next one runs the following day and sends subscription.charge_succeeded.
  7. Manual chargeCharge the subscription. Expect charge_created and a payment.authorised webhook.
  8. Cancel and reactivateCancel the subscription, then reactivate it. Check that nextChargeAt is one interval after the last charge.

What behaves differently in test

Test payments settle on authorised

A paid test link stays at authorised. You will not see paid in test. Treat authorised as success in both environments. See Payment lifecycle and states. Verified

Refunds and cancellations are slow

A refund answered refund_requested at once and then stayed unsettled for more than 11 hours. A refund and a cancel requested on the same day both still showed refund_requested and cancel_requested more than 24 hours later. Verified Plorea says this is expected and that the final states are refunded and cancelled. Stated by Plorea We do not know if live is faster. Open question

Size your polling in hours

A test that waits a few minutes for refunded will fail. Assert on refund_requested instead, and book the refund on that state.

Links do not expire in the status

A link past its expiry still reports an open status. To test expiry, read expired from GET /pay/{paymentLinkId}. Verified

Abandoned sessions stay created

A checkout session that nobody completes stays created for ever. Clean up on your side. Verified

What cannot be reproduced in test

A declined recurring charge

You cannot make a stored card decline on a later charge with Adyen's public test cards. Not observable in test

  • Adyen triggers refusals only through the holder name or a test acquirer response code. Both are fields of the first payment request. For a stored card, the first request is the setup. So the setup fails, and no card is stored.
  • A published test card approves or fails at once. Each has a future expiry. No card can expire after you store it.
  • Plorea charges the stored card on the server. It passes neither trigger through.

As a result, these shapes cannot be produced in test: the 402 body of a declined manual charge, a payment_failed subscription and the state after the last retry. The past_due shape (a filled failureReason, a non-zero retryCount) was seen once in production. Verified 2026-10-01 The subscription.charge_failed webhook was seen in test for a stored card that was gone, not for a decline. Verified

Write dunning code that tolerates small differences. Branch on status. Do not require failureReason. See Failed charges and dunning.

Requested from Plorea

A test card that stores successfully and declines on a later charge, or a passthrough of Adyen's RequestedTestAcquirerResponseCode on POST /subscriptions/{id}/charge. Proposal

Other items we could not observe in test: a live value of environment, a live client key, an Android Drop-in on a real device, and the final state after a refund settles.

Receive webhooks on your laptop

Plorea needs a public HTTPS URL. Use a tunnel to forward it to your local server.

  1. Start your app locallyFor example on port 8000, with the webhook route at /plorea/webhook.
  2. Start a tunnelUse any tunnel tool. Keep a stable hostname if the tool supports one, so you do not need to re-register.
  3. Register the tunnel URL as your test URLSend it to Plorea. Registration is manual. Ask for a separate test URL so live is not affected.
  4. Set the test signing secretPut it in your local environment. Never commit it.
  5. Pay a test linkA signed payment.authorised arrives in a few seconds.
# Any tunnel works. Two common ones:
cloudflared tunnel --url http://localhost:8000
# or
ngrok http 8000

# Register: https://<your-tunnel-host>/plorea/webhook

To replay an event without Plorea, sign a stored body yourself. See Verify the signature.

Test without the network: SDK fakes

The PHP SDK has a built-in fake client. Plorea::fake() swaps the HTTP client for an in-memory fake. No request leaves your test suite. Every endpoint has a default response, and every call is recorded.

use MemberFlow\Plorea\Data\Amount;
use MemberFlow\Plorea\Facades\Plorea;

Plorea::fake();

$link = Plorea::payments()
    ->link('order-1001', 'Annual membership', Amount::nok(50000), 'https://example.com/return')
    ->merchant(orgNr: '999999999')
    ->create();

Plorea::assertSent('POST payments/link');
Plorea::assertSent(fn ($request) => $request->input('amount') === 50000);
Plorea::assertNotSent('payments/refund');
Plorea::assertSentCount(1);
# No fake server exists for raw HTTP.
# Use the JSON shapes on the API reference page as stub responses
# in your own HTTP mocking library.
// No official Node fake. Stub fetch with the documented shapes:
globalThis.fetch = async (url, init) => {
  if (url.includes('/payments/status/')) {
    return new Response(JSON.stringify({ reference: 'order-1001', status: 'authorised', amount: 1000, currency: 'NOK' }));
  }
  return new Response(JSON.stringify({ error: 'Payment not found' }), { status: 404 });
};

Stub responses and errors

Pass an array of pattern => response. A response can be an array, a callable, or an exception to throw. Patterns use wildcards and can start with a method. The first match wins.

use MemberFlow\Plorea\Exceptions\ChargeFailedException;
use MemberFlow\Plorea\Exceptions\NotFoundException;

Plorea::fake([
    'payments/status/*'      => ['reference' => 'order-1001', 'status' => 'authorised'],
    'POST payments/link'     => fn ($request) => ['paymentLinkId' => 'pl_1', 'url' => 'https://pay.example.com/1'],
    'subscriptions/*/charge' => new ChargeFailedException('Charge failed: Refused', 402),
    'payment-methods/*'      => new NotFoundException('Payment method not found', 404),
]);

A useful detail: the fake remembers references it created links for. A status lookup for such a reference answers an open link. Any other reference throws NotFoundException, like a live 404. So firstOrCreate() works in tests without stubs.

Call Http::preventStrayRequests() in your test suite. Any Plorea call you forgot to fake then fails loudly instead of reaching the network.

Test your webhook listeners

Post a stored body to your route with a signature you compute in the test. Or set PLOREA_WEBHOOK_VERIFY=false in your test configuration only.

$body = json_encode([
    'eventId' => 'evt_test_1',
    'type'    => 'payment.authorised',
    'data'    => ['reference' => 'order-1001', 'status' => 'authorised'],
]);

$this->call('POST', '/plorea/webhook', [], [], [], [
    'CONTENT_TYPE'            => 'application/json',
    'HTTP_X_PLOREA_SIGNATURE' => base64_encode(hash_hmac('sha256', $body, config('plorea.webhooks.secret'), true)),
], $body)->assertOk();

Never put real credentials in tests

No API keys, signing secrets, real signatures, client keys or real references in test code, fixtures or comments. Use obvious fakes such as plr_test_FAKE… and test_FAKE….
