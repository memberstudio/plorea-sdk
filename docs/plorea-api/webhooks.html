Integration

Webhooks

Plorea sends a signed HTTP POST to your server when a payment is authorised, fails or is refunded, and when the scheduler charges a subscription. This guide shows how to register an endpoint, verify each delivery, and process events safely.

The one rule: a webhook is a ping, not a fact

Use a webhook to learn that something changed. Then read the current state from the API before you move money or grant access. Delivery is best-effort, the same event can arrive twice, and some state changes send no webhook at all.

How delivery works

Register an endpoint

Registration is manual. No API exists for it. Verified

  1. Expose an HTTPS endpointFor example https://api.example.com/plorea/webhook. It must accept POST with a JSON body.
  2. Send the URL to Plorea through a secure channelName the environment the URL is for: test or live.
  3. Receive the signing secretStore the secret in your environment configuration. Never commit it. The secret is not your API key and not your tenant ID.
  4. Ask for one URL per environmentBy default a tenant has one registered URL. Plorea sets up a separate URL for each environment on request. Stated by Plorea

Missing deliveries? Check the registered URL first

A tenant registered against one environment sends nothing to the other. If test deliveries do not arrive, confirm which URL Plorea has on file before you debug your code. Verified

Test and live may share one signing secret. Confirm this with Plorea for your account. Stated by Plorea

Request headers

Each delivery carries three Plorea headers. A real delivery has no Authorization header. Verified

HeaderContent
x-plorea-signatureBase64-encoded HMAC-SHA256 of the raw request body, keyed with your signing secret. 44 characters.
x-plorea-event-idevt_ followed by 32 hex characters. The same value as eventId in the body.
x-plorea-eventThe event type, for example payment.authorised. The same value as type in the body.
Content-Typeapplication/json

The signature covers the body only

The headers are outside the signature. An attacker who replays a genuine body with its genuine signature can put any value in x-plorea-event-id. Read eventId and type from the verified body. Never deduplicate on the header. Verified

The event envelope

Every event has the same outer shape. The data object depends on type.

eventId string
Unique ID of this event. evt_ plus 32 hex characters. Use it as your idempotency key.
createdAt string, ISO 8601
When Plorea created the event. It is not the creation time of the payment.
tenantId string
The tenant the event belongs to.
type string
The event type. See the catalogue below.
data object
The event payload.

Treat a failed link as closed

Whether the customer can try again on the same link after a decline is not confirmed. Open question Do not depend on it. On payment.failed, offer a new link on a suffixed reference. Still handle a later payment.authorised for the failed reference: book it idempotently on the reference. See Payment lifecycle.

payment.refunded

Plorea sends this event when a refund settles. Settlement can take more than 11 hours in test. Verified We have not captured the payload. Expect the same data shape as the other payment events, with the payment's own reference. Open question

Do not wait for this event to update your books. Book the refund when POST /payments/refund answers refund_requested. See Refunds and cancellations.

Do not look up a scheduler charge as a payment

The reference of a scheduler charge does not resolve on GET /payments/status/{reference}. The call answers 403, later 404. Read the charge from GET /subscriptions/{id}/charges instead. A manual charge reference does resolve. Verified

Plorea states that charge webhooks include the subscription's merchantOrgNr when one is set. Our captures predate that field. Stated by Plorea

What is not sent

Plorea sends no webhook for the transitions below. You must poll for them. Stated by Plorea

TransitionHow to detect it
Card setup succeeds or fails (pending_setup → active | failed)GET /payment-methods/{id} after the customer returns, and on a schedule until expiresAt.
Subscription cancelledThe cancel call returns the new state synchronously.
Subscription reactivatedThe reactivate call returns the new state synchronously.
A scheduler charge failsPoll GET /subscriptions/{id}. Compare nextChargeAt with now. See Failed charges and dunning.
A payment link expiresThe status never reports expired. Use expiresAt from the create response, or expired on GET /pay/{id}.
A cancellation settlesNo payment.cancelled event is known. Poll the status. Open question

Gap: a declined recurring charge is silent

The most important failure in recurring billing sends no event. A subscription.charge_failed event would remove the need to poll. Proposal See Gaps and proposals.

Verify the signature

Verify every delivery before you trust it. The algorithm is: base64(HMAC-SHA256(key = secret, message = raw body bytes)). Compare the result with x-plorea-signature in constant time. Verified

  1. Read the raw bodyRead the bytes exactly as they arrived. Do not parse and re-serialise the JSON first.
  2. Use the secret verbatim as the keyUse the characters of the secret as Plorea gave it to you. Do not hex-decode or base64-decode it. The decoded-key variant does not match.
  3. Compute the HMACHMAC-SHA256 over the raw body. Encode the binary digest as standard base64.
  4. Compare in constant timeUse hash_equals in PHP or crypto.timingSafeEqual in Node. A normal string compare leaks timing.
  5. Fail closedReject the request with 401 or 403 if the header is missing, the secret is not configured, or the values differ.

Re-encoded bodies break the signature

A JSON body parser, a proxy that rewrites the body, or an added trailing newline changes the bytes. The HMAC then fails while the payload still looks valid. If a delivery you believe is genuine fails, check the secret and the raw body before you suspect the algorithm. A replay test proved that a genuine delivery passes and a one-byte edit fails. Verified

// Plain PHP, without the SDK:
$raw       = file_get_contents('php://input');
$given     = $_SERVER['HTTP_X_PLOREA_SIGNATURE'] ?? '';
$secret    = getenv('PLOREA_WEBHOOK_SECRET');
$expected  = base64_encode(hash_hmac('sha256', $raw, $secret, true));

if ($secret === false || $secret === '' || ! hash_equals($expected, $given)) {
    http_response_code(403);
    exit;
}

$event = json_decode($raw, true, flags: JSON_THROW_ON_ERROR);
import express from 'express';
import crypto from 'node:crypto';

const app = express();

// Keep the raw bytes. express.json() would re-encode them.
app.post('/plorea/webhook', express.raw({ type: 'application/json' }), async (req, res) => {
  const secret = process.env.PLOREA_WEBHOOK_SECRET;
  const given = Buffer.from(req.get('x-plorea-signature') ?? '', 'utf8');
  if (!secret) return res.sendStatus(403); // fail closed

  const expected = Buffer.from(
    crypto.createHmac('sha256', secret).update(req.body).digest('base64'),
    'utf8',
  );

  if (given.length !== expected.length || !crypto.timingSafeEqual(given, expected)) {
    return res.sendStatus(403);
  }

  const event = JSON.parse(req.body.toString('utf8'));
  // Store durably, then answer. Process in a job.
  try {
    await inbox.store(event); // e.g. the plorea_events table below
  } catch (err) {
    // Not stored: the event is lost unless reconciliation finds it.
    console.error('Plorea webhook not stored', err);
    return res.sendStatus(500);
  }
  res.sendStatus(200);
});

Respond fast with 2xx

Return 200 as soon as you have verified and stored the delivery. Do slow work in a background job.

Failed deliveries are not redelivered

Plorea does not retry a delivery that fails or times out. Stated by Plorea An error response does not buy you a second attempt. It loses the event. So:

  • Accept every verified delivery with 200, also when your own processing fails.
  • Store the raw event first. Retry your own processing from what you stored.
  • Run the reconciliation job below.

The Laravel SDK's controller answers 200 [accepted] to a verified delivery, also to a body it cannot parse. It dispatches your listeners before it answers. A synchronous listener that throws turns the answer into a 500, and Plorea does not redeliver. Keep listeners small: store the event and queue the work. Implement ShouldQueue on a listener class, or dispatch a job from the closure.

Deduplicate on eventId

The same event can arrive more than once. A webhook, a status poll and the customer's return page can also race on the same payment. Make every handler idempotent.

  • Store eventId from the body with a unique constraint.
  • Keep "received" and "processed" apart. Set processed_at only after the work succeeds. Skip an event only when it is processed. Retry unprocessed events from a scheduled job.
  • Book money idempotently on the payment reference, not on the event.
# Deduplication happens in your code. A database example:
#   CREATE TABLE plorea_events (
#     event_id   text PRIMARY KEY,
#     type       text NOT NULL,
#     payload    jsonb NOT NULL,
#     received_at timestamptz NOT NULL DEFAULT now(),
#     processed_at timestamptz
#   );
# INSERT ... ON CONFLICT (event_id) DO NOTHING;
use Illuminate\Support\Facades\Cache;
use Illuminate\Support\Facades\Event;
use MemberFlow\Plorea\Events\PaymentStatusUpdated;
use MemberFlow\Plorea\Facades\Plorea;

Event::listen(PaymentStatusUpdated::class, function (PaymentStatusUpdated $event) {
    // eventId is read from the signed body, never from the header.
    $key = "plorea:webhook:{$event->eventId}";

    if (Cache::has($key)) {
        return; // already processed
    }

    // The webhook is a ping. Read the authoritative state.
    // If this throws, nothing is marked, so a retry processes the event again.
    $status = Plorea::payments()->status($event->reference);

    if ($status->isPaid()) {
        // Compare $status->amount with what you expect, then book
        // idempotently on the reference.
    }

    // Mark as processed only after the work succeeded.
    Cache::put($key, true, now()->addDay());
});
// Runs from a job for each stored event, and again from a scheduled
// job for any event with processed_at still null.
async function handle(event) {
  const { rows } = await db.query(
    'SELECT processed_at FROM plorea_events WHERE event_id = $1',
    [event.eventId],
  );
  if (rows[0]?.processed_at) return; // already processed

  if (event.type.startsWith('payment.')) {
    const res = await fetch(
      `https://payments.plorea.no/payments/status/${encodeURIComponent(event.data.reference)}?platform=acme`,
      { headers: { Authorization: `Bearer ${process.env.PLOREA_API_KEY}`, 'X-Environment': 'test' } },
    );
    if (!res.ok) throw new Error(`Status read failed: ${res.status}`); // stays unprocessed
    const payment = await res.json();
    if (payment.status === 'authorised' || payment.status === 'paid') {
      await bookPayment(payment.reference, payment.amount); // idempotent
    }
  }

  // Mark as processed only after the work succeeded.
  await db.query(
    'UPDATE plorea_events SET processed_at = now() WHERE event_id = $1',
    [event.eventId],
  );
}

The SDK fires SubscriptionChargeSucceeded for a scheduler charge and does not also fire PaymentStatusUpdated. Two events for one charge would make listeners book it twice.

Reconcile by polling

Webhooks can be lost, and some transitions send none. Run a scheduled job that reads state directly. This is not over-engineering. It is the only way to see a failed scheduler charge.

WhatCallHow often
Open payment linksGET /payments/status/{reference}Every few minutes until paid or past expiresAt.
Card setupsGET /payment-methods/{id}Every few minutes until active or failed.
Refunds and cancels in flightGET /payments/status/{reference}Hourly. Settlement can take more than 11 hours.
SubscriptionsGET /subscriptions?externalId=… without a status filterHourly. Flag any that is payment_failed. Also flag any that is not canceled and has nextChargeAt in the past. A status=active filter hides payment_failed and overdue trials.
 
// Open links.
Plorea::payments()->status($invoice->reference);

// Subscriptions that are overdue or in payment failure.
Plorea::subscriptions()->needingAttention($workspace->externalId);

  • Pay a test payment link. Plorea sends a real signed payment.authorised to your test URL.
  • Pay with a card Adyen declines to receive payment.failed. See Testing.
  • Create a subscription with a one-day interval to receive subscription.charge_succeeded the next day.
  • Expose a local server through a tunnel and register the tunnel URL as your test URL with Plorea.

], $body)->assertOk();

Turning off verification

The SDK has PLOREA_WEBHOOK_VERIFY=false for a staging system that waits for its secret. Never use it in production. Without verification, anyone who knows the URL can post fake events.

Security checklist

  • Verify the signature on the raw body, in constant time. Fail closed.
  • Deduplicate on eventId from the body.
  • Re-read state from the API before you act.
  • Compare the amount with what you expect before you book money.
  • Rate-limit the endpoint. The SDK accepts extra middleware in plorea.webhooks.middleware, for example throttle:60,1.
  • Keep the signing secret out of source control and logs.
